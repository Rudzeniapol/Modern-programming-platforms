# Лабораторная работа №2 — Менеджер задач (SPA + REST API)

Приложение «список задач» с архитектурой **Single Page Application на клиенте** и
**REST API на сервере**. Разметку целиком строит браузер, данные ходят между клиентом
и сервером в формате **JSON**, файлы — в формате **multipart/form-data**. Любое
действие пользователя (создание, изменение, удаление, загрузка файла, фильтрация)
выполняется через `fetch` и **не перезагружает страницу**.

Весь проект разворачивается тремя контейнерами Docker: база данных, REST API и
SPA за nginx.

## Стек

| Слой | Технологии |
|------|-----------|
| Клиент | React 19 + Vite, без сторонних UI- и HTTP-библиотек |
| Сервер | Node.js 22 + Express, multer (приём файлов), драйвер `pg` |
| База данных | PostgreSQL 16 |
| Инфраструктура | Docker, Docker Compose, nginx (статика + reverse proxy) |

## Возможности

* полный цикл CRUD над задачами: создание, чтение, изменение, удаление;
* поля задачи — название, описание, статус, ожидаемая дата завершения;
* три статуса: «К выполнению», «В работе», «Выполнено», быстрая смена прямо из списка;
* фильтрация по статусу (вкладки со счётчиками), поиск по названию и описанию, сортировка
  (срок / дата создания / название) — всё выполняется на сервере в SQL;
* вложения: загрузка нескольких файлов к задаче, скачивание под исходным именем, удаление;
* подсветка просроченных задач и задач со сроком «сегодня»;
* серверная валидация всех входящих данных и вывод сообщений об ошибках рядом с
  конкретными полями формы.

## Запуск

```bash
cd Lab2
docker compose up --build
```

* SPA — <http://localhost:8088>
* REST API — <http://localhost:3000/api> (открыт наружу, чтобы обращаться к нему напрямую
  из `curl` или Postman)

Порты и параметры БД переопределяются через `.env` (шаблон — `.env.example`):

```bash
cp .env.example .env   # при необходимости поменять WEB_PORT / API_PORT / пароль БД
```

Остановка и полная очистка вместе с данными:

```bash
docker compose down          # остановить
docker compose down -v       # остановить и удалить тома (БД и загруженные файлы)
```

### Запуск без Docker (для разработки)

Нужен запущенный PostgreSQL. Схему таблиц API создаёт сам при старте.

```bash
# терминал 1 — API
cd Lab2/server
npm install
DATABASE_URL=postgres://tasks:tasks@localhost:5432/tasks npm run dev

# терминал 2 — клиент
cd Lab2/client
npm install
npm run dev        # http://localhost:5173, запросы /api проксируются на :3000
```

Dev-сервер Vite проксирует `/api` на Node (см. `client/vite.config.js`), поэтому клиент и
API остаются на одном origin и CORS не нужен. Если клиент всё же запускается на чужом
origin, на сервере достаточно задать переменную `CORS_ORIGIN`.

## Архитектура

```
браузер ──► nginx (контейнер web, порт 8088)
              ├── /            → статика собранного SPA (index.html, JS, CSS)
              └── /api/*       → proxy_pass на контейнер api
                                    │
                                    ▼
                          Express REST API (контейнер api, порт 3000)
                                    ├── PostgreSQL (контейнер db)  — задачи и метаданные файлов
                                    └── том uploads               — сами файлы
```

Клиент и API живут за одним origin, поэтому CORS в рабочей конфигурации не используется.
Загруженные файлы и база лежат в именованных томах Docker и переживают пересборку образов.

## REST API

Базовый путь — `/api`. Тело запросов и ответов — JSON, кроме загрузки файлов
(`multipart/form-data`) и скачивания вложения (бинарный поток).

| Метод | Путь | Назначение | Успех | Ошибки |
|-------|------|------------|-------|--------|
| GET | `/api/meta` | справочник статусов и лимиты загрузки | 200 | — |
| GET | `/api/health` | проба живости (используется healthcheck-ом) | 200 | 503 |
| GET | `/api/tasks?status=&q=&sort=` | список задач и счётчики для вкладок | 200 | 400 |
| POST | `/api/tasks` | создание задачи (JSON **или** multipart с файлами) | 201 + `Location` | 400, 415 |
| GET | `/api/tasks/:id` | одна задача | 200 | 400, 404 |
| PUT | `/api/tasks/:id` | полная замена полей задачи | 200 | 400, 404, 415 |
| PATCH | `/api/tasks/:id` | частичное изменение (смена статуса) | 200 | 400, 404, 415 |
| DELETE | `/api/tasks/:id` | удаление задачи вместе с вложениями | 204 | 400, 404 |
| POST | `/api/tasks/:id/attachments` | загрузка файлов (multipart/form-data) | 201 + `Location` | 400, 404 |
| GET | `/api/tasks/:id/attachments/:fileId` | скачивание файла под исходным именем | 200 | 400, 404 |
| DELETE | `/api/tasks/:id/attachments/:fileId` | удаление файла | 204 | 400, 404 |

Коды ответов используются по назначению: `201 Created` с заголовком `Location` на
создание, `204 No Content` на удаление, `400 Bad Request` на некорректные данные,
`404 Not Found` на отсутствующий ресурс, `415 Unsupported Media Type` на неподдерживаемый
`Content-Type`, `500` — только на непредвиденные ошибки сервера.

### Формат ошибки

Любая ошибка возвращается в одном и том же виде, поэтому клиент разбирает её единым кодом:

```json
{
  "error": {
    "status": 400,
    "message": "Проверьте заполнение полей задачи",
    "fields": {
      "title": "Введите название задачи",
      "dueDate": "Некорректная дата (ожидается формат ГГГГ-ММ-ДД)"
    }
  }
}
```

`message` показывается плашкой вверху страницы, а содержимое `fields` — под
соответствующими полями формы.

### Примеры запросов

```bash
# создание задачи (JSON)
curl -i -X POST http://localhost:3000/api/tasks \
     -H 'Content-Type: application/json' \
     -d '{"title":"Сдать ЛР №2","status":"in_progress","dueDate":"2026-10-01"}'

# создание задачи вместе с файлами (multipart/form-data)
curl -i -X POST http://localhost:3000/api/tasks \
     -F 'title=Задача с файлом' -F 'attachments=@отчёт.pdf'

# смена статуса
curl -i -X PATCH http://localhost:3000/api/tasks/<id> \
     -H 'Content-Type: application/json' -d '{"status":"done"}'

# удаление
curl -i -X DELETE http://localhost:3000/api/tasks/<id>
```

## Проверка входящих данных

Валидация выполняется на сервере (`server/src/lib/validation.js`) и покрывает всё, что
приходит от клиента:

* **тело запроса** — тип каждого значения (в JSON вместо строки может прийти число,
  объект или массив), обязательность названия, длина названия (≤ 200) и описания (≤ 2000),
  принадлежность статуса справочнику, календарная корректность даты (`2026-02-31`
  проходит по формату, но такой даты не существует), а также отказ на неизвестные поля;
* **параметры выборки** — `status`, `sort` и `q` проверяются по белому списку; неверное
  значение даёт `400`, а не молчаливую подстановку значения по умолчанию;
* **идентификаторы** — формат UUID проверяется до обращения к БД, иначе Postgres ответил
  бы ошибкой приведения типа и клиент получил бы `500` вместо `400`;
* **файлы** — размер (до 10 МБ) и количество (до 5 за запрос) ограничены multer,
  принимается только поле `attachments`;
* **Content-Type** — тело принимается только как `application/json` или
  `multipart/form-data`, иначе `415`.

Те же ограничения продублированы в схеме БД (`CHECK` на длину названия и допустимые
статусы) — данные остаются корректными, даже если запись пойдёт в обход API.

На клиенте дополнительно проверяются размер и количество выбранных файлов — чтобы не
отправлять по сети заведомо негодные данные. Решающее слово всегда за сервером.

## Хранение данных

```
tasks
  id          UUID PRIMARY KEY
  title       TEXT NOT NULL      CHECK (length BETWEEN 1 AND 200)
  description TEXT NOT NULL      CHECK (length <= 2000)
  status      TEXT NOT NULL      CHECK (status IN ('todo','in_progress','done'))
  due_date    DATE
  created_at, updated_at TIMESTAMPTZ

attachments
  id            UUID PRIMARY KEY
  task_id       UUID → tasks(id) ON DELETE CASCADE
  original_name TEXT             — имя, под которым файл отдаётся при скачивании
  stored_name   TEXT UNIQUE      — имя на диске (UUID)
  size, mime_type, uploaded_at
```

* Задача и её вложения создаются и удаляются в одной транзакции.
* Записи о вложениях уходят вместе с задачей по `ON DELETE CASCADE`, сами файлы
  удаляются с диска уже после успешного коммита.
* На диск файлы кладутся под сгенерированным UUID-именем: исходное имя пользователя на
  файловую систему не попадает, поэтому path traversal и коллизии имён исключены.
  Оригинальное имя хранится в БД и подставляется при скачивании.
* Поиск использует `ILIKE`, спецсимволы `%` и `_` экранируются — иначе запрос «100%»
  находил бы вообще всё.

## Отличия от лабораторной работы №1

| | ЛР №1 | ЛР №2 |
|---|-------|-------|
| Разметка | EJS на сервере, полный HTML в ответе | React в браузере, сервер отдаёт только JSON |
| Обмен данными | HTML-формы + редиректы (POST/Redirect/GET) | `fetch`: JSON и multipart/form-data |
| Обновление страницы | каждое действие перезагружает страницу | страница не перезагружается |
| HTTP-методы | только GET и POST (ограничение HTML-форм) | GET, POST, PUT, PATCH, DELETE |
| Ответы сервера | HTML-страницы, редиректы | коды 200/201/204/400/404/415/500 и JSON |
| Хранение | файл `data/tasks.json` | PostgreSQL |
| Развёртывание | `npm start` | `docker compose up` — три контейнера |
