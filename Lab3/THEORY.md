# Теория к лабораторной работе №3
### Роли и временные ключи, HTTP-семантика ошибок, защита доступа, структурированные логи, CI

**Для человека, который знает C#/.NET.** Почти у каждого пункта есть аналогия из ASP.NET Core:
ЛР №3 по сути — это то, что в .NET дают `JwtBearer` + `[Authorize]` + `ProblemDetails` +
Identity Lockout + `RateLimiter` + Serilog + GitHub Actions, только написанное руками на Express.

---

## 0. Что сделано (на одном дыхании)

Берём приложение из ЛР №2 (SPA на React + REST API на Express + PostgreSQL в Docker) и
закрываем его входом:

* пользователь **регистрируется / входит** по email и паролю и получает **два временных ключа**:
  короткий **access-токен** (JWT, 15 минут) — им подписывается каждый запрос, и длинный
  **refresh-токен** (7 дней, в HttpOnly-cookie) — им access-токен продлевается;
* у каждого пользователя одна из **трёх ролей** — `user`, `manager`, `admin`; роль определяет
  набор **прав**, а сервер проверяет права на каждом запросе и для каждой задачи;
* каждая ошибка возвращается с **правильным HTTP-кодом**, нужными заголовками и в стандартном
  формате **RFC 9457** (`application/problem+json`);
* вход защищён от **подбора пароля** (блокировка после 5 неудач, лимит по IP, лимиты частоты),
  у пользователя видны и управляются **активные подключения** (сессии, лимит 5 штук),
  забытый пароль восстанавливается **по ссылке из письма**;
* всё, что происходит, пишется в **структурированный JSON-журнал** со сквозным `reqId`;
* на каждый push GitHub Actions запускает **линтер, 46 автотестов на настоящем PostgreSQL,
  сборку и аудит зависимостей**.

**Фраза для защиты:** «Аутентификация — по временным ключам: короткоживущий JWT плюс
одноразовый refresh-токен с ротацией, привязанные к серверной сессии. Авторизация — RBAC с
тремя ролями и правами уровня own/any. Ошибки — по семантике HTTP в формате RFC 9457.
Вход защищён блокировкой и rate limiting, сессии контролируются, доступ восстанавливается через
email. Логи — JSON через pino с корреляцией запросов. Качество кода проверяет CI».

## 2. Путь одного запроса через систему

Возьмём `PATCH /api/tasks/:id {"status":"done"}` от менеджера.

```
1. nginx          назначает $request_id, пишет его в X-Request-Id, проксирует в api
2. requestLogger  берёт reqId из заголовка (или генерирует), создаёт req.log, вернёт X-Request-Id в ответе
3. cors           (в Docker выключен — клиент и API на одном origin)
4. express.json   разбирает тело; битый JSON → ошибка → 400
5. cookieParser   разбирает cookie (нужна только /api/auth/*)
6. tasks router   router.use(authenticate):
                    • нет заголовка Authorization              → 401 + WWW-Authenticate
                    • JWT подделан / истёк                      → 401 invalid_token / token_expired
                    • сессия sid из JWT отозвана или юзер заблокирован → 401 session_revoked
                    • иначе req.user = {id, role, …} из БД
7. requireJson    Content-Type не JSON → 415
8. withTask('update')  грузит задачу:
                    • нельзя даже прочитать → 404
                    • прочитать можно, менять нельзя → 403
9. обработчик     валидация полей (ошибки → 422), UPDATE в БД, лог task.updated, 200 + JSON
10. errorHandler  (если где-то выше была ошибка) → правильный код + problem+json
11. requestLogger пишет итоговую строку: метод, url, статус, время, userId, reqId
```

Аналогия: это ровно конвейер ASP.NET Core — `UseRouting → UseAuthentication → UseAuthorization →
endpoint`, где каждое звено может «закоротить» ответ.

**Порядок важен:** права проверяются **до** multer (`withTask` стоит раньше `uploadAttachments`),
чтобы сервер не принимал 50 МБ файлов от того, кому всё равно ответит 403.

## 3. Пункт 1 — модель доступа: роли и временные ключи

### 3.1. Аутентификация ≠ авторизация

* **Аутентификация** — «кто ты?». Проверяем пароль, выдаём ключ, на каждом запросе проверяем ключ.
  Провал → **401 Unauthorized** (название кода историческое, по смыслу это «unauthenticated»).
* **Авторизация** — «что тебе можно?». Роль и права. Провал → **403 Forbidden**.

В коде: аутентификация — `middleware/auth.js → authenticate`, авторизация — `requirePermission`
и `canOnTask` из `lib/roles.js`.

### 3.2. RBAC — Role-Based Access Control

Права не выдаются пользователю напрямую: пользователю выдаётся **роль**, у роли — **набор прав**.
Это упрощает администрирование: поменял роль — поменялись все права.

```js
// lib/roles.js
user:    tasks:read:own, tasks:create, tasks:update:own, tasks:delete:own
manager: всё от user + tasks:read:any, tasks:update:any, users:read
admin:   все права (включая tasks:delete:any, users:manage)
```

| | user | manager | admin |
|---|:-:|:-:|:-:|
| свои задачи (CRUD) | ✔ | ✔ | ✔ |
| видеть все задачи | | ✔ | ✔ |
| менять чужие задачи | | ✔ | ✔ |
| удалять чужие задачи | | | ✔ |
| видеть пользователей | | ✔ | ✔ |
| менять роли, блокировать, завершать чужие сессии, снимать блокировку входа | | | ✔ |

**Почему права, а не проверки «если роль == admin»:** код маршрута спрашивает «есть ли право
`users:manage`», а не «какая роль». Если завтра появится роль `auditor`, достаточно дописать её в
`roles.js` — маршруты менять не надо. В .NET то же самое — **policy-based authorization**
(`AddPolicy("CanManageUsers", …)`) вместо `[Authorize(Roles="Admin")]`.

**Уровни `:own` и `:any`** — это уже элемент **ABAC** (attribute-based): решение зависит не только
от роли, но и от атрибута ресурса (`task.ownerId === user.id`). Функция:

```js
function canOnTask(user, action, task) {
  if (hasPermission(user, `tasks:${action}:any`)) return true;
  return hasPermission(user, `tasks:${action}:own`) && task.ownerId === user.id;
}
```

В .NET это `IAuthorizationHandler` с resource-based authorization.

### 3.3. Почему на чужую задачу — 404, а не 403

Если на чужую задачу отвечать 403, то по разнице «403 — существует, 404 — нет» можно перебором
UUID узнавать, какие задачи есть в системе. Поэтому:

* **не можешь даже прочитать** → 404 (для тебя её нет);
* **читать можешь, а менять нельзя** (менеджер пытается удалить чужую) → 403.

Так же сделали GitHub (приватный репозиторий чужому — 404).

### 3.4. Проверка прав на клиенте — только косметика

`client/src/lib/permissions.js` прячет кнопки «Удалить» и т.п. Но **безопасность обеспечивает
только сервер**: через DevTools или curl кнопку «нажать» можно всегда, и сервер ответит 403/404.
Правило: *клиенту никогда не доверяем*.

### 3.5. Что такое «временный ключ» и почему их два

**Временный ключ** — токен доступа с ограниченным сроком жизни. Если его украдут, он скоро сам
станет бесполезен. Но если ключ живёт 15 минут, пользователю пришлось бы логиниться каждые
15 минут. Классическое решение (OAuth 2.0) — **пара ключей**:

| | access-токен | refresh-токен |
|---|---|---|
| формат | JWT (подписанный JSON) | `<id сессии>.<случайный секрет 32 байта>` |
| срок | 15 минут | 7 дней, продлевается при использовании |
| где хранится у клиента | **в памяти JS** (переменная в `api.js`) | **HttpOnly-cookie** |
| куда отправляется | в каждый запрос: `Authorization: Bearer …` | только на `/api/auth/*` (`Path=/api/auth`) |
| что даёт | доступ к API | новый access-токен |
| в БД | не хранится | хранится **SHA-256** от секрета в `sessions.refresh_hash` |

### 3.6. JWT — как устроен

JWT = три части в Base64URL через точку: `header.payload.signature`.

```
header:    {"alg":"HS256","typ":"JWT"}
payload:   {"sub":"<id пользователя>","sid":"<id сессии>","role":"manager",
            "iss":"spp-lab3-api","aud":"spp-lab3-client",
            "iat":1790333935,"exp":1790334835,"jti":"<уникальный id токена>"}
signature: HMAC-SHA256(header + "." + payload, JWT_SECRET)
```

* Payload **не зашифрован**, только подписан — любой может его прочитать (jwt.io), но не может
  изменить: изменил роль на `admin` → подпись не сойдётся → 401.
* `exp` — время истечения; библиотека `jsonwebtoken` сама отвергает истёкшие токены
  (`TokenExpiredError` → наш код `token_expired`).
* `iss`/`aud` проверяются — токен, выпущенный для другой системы, не подойдёт.
* Алгоритм жёстко задан `algorithms: ['HS256']` — защита от классической атаки `alg: none`.
* **HS256** — симметричная подпись (один секрет подписывает и проверяет). Подходит, когда токены
  выпускает и проверяет один сервис. Если бы проверяли многие сервисы — брали бы RS256/ES256
  (закрытый ключ у выпускающего, открытый у всех).

Код: `lib/tokens.js → signAccessToken / verifyAccessToken`.
В .NET: `AddJwtBearer(o => o.TokenValidationParameters = …)`.

### 3.7. Stateless JWT vs. наша схема «JWT + сессия в БД»

Чистый JWT **stateless**: сервер проверяет только подпись и `exp`, в БД не ходит. Плюс —
скорость. Минус — **токен нельзя отозвать**: выход, блокировка пользователя, смена роли не
действуют, пока токен не истечёт.

У нас каждый access-токен содержит `sid`, и `authenticate` делает один запрос:

```sql
SELECT … FROM sessions s JOIN users u … WHERE s.id = $sid AND s.revoked_at IS NULL AND s.expires_at > now()
```

Поэтому:
* выход, «завершить сессию», блокировка пользователя действуют **мгновенно**;
* роль берётся **из БД**, а не из токена → админ сменил роль — права изменились на следующем же
  запросе (тест «администратор меняет роль — права действуют сразу»).

Компромисс осознанный: один индексированный запрос на каждое обращение в обмен на полный
контроль над сессиями — это и есть требование «контроль активных подключений».

### 3.8. Refresh-токен: ротация и обнаружение кражи

**Ротация** — каждый `POST /api/auth/refresh` выдаёт **новый** refresh-токен, а старый
становится недействительным. `sessionRepository.rotate` делает это атомарно:

```sql
UPDATE sessions SET prev_refresh_hash = refresh_hash, refresh_hash = $new, rotated_at = now() …
 WHERE id = $1 AND refresh_hash = $expected AND revoked_at IS NULL
```

Условие `refresh_hash = $expected` гарантирует: из двух одновременных запросов с одним токеном
выиграет ровно один (оптимистическая блокировка, как `ConcurrencyToken` в EF).

**Reuse detection** (обнаружение повторного использования). Если предъявлен токен, который уже
был заменён, — значит, им пользуются двое: владелец и вор. Мы не знаем, кто из них кто, поэтому
**закрываем сессию целиком** (событие `auth.refresh.reuse_detected`). Вор теряет доступ,
владелец просто входит заново.

**Окно гонки (30 с, `REFRESH_REUSE_GRACE_SEC`).** Две вкладки браузера могут одновременно
отправить refresh со старым токеном. Чтобы это не считалось кражей: если предъявлен
*предыдущий* токен в течение 30 секунд после ротации — выдаём только access-токен, cookie не
трогаем. Логика — в `authService.refresh`.

### 3.9. Почему access в памяти, а refresh в HttpOnly-cookie

Две главные атаки на браузерные токены:

* **XSS** (внедрённый чужой JS на странице) — может прочитать всё, что доступно JS:
  `localStorage`, переменные. Поэтому **refresh-токен в `HttpOnly`-cookie** — JS его не видит
  вообще. Access-токен в памяти XSS украсть может, но он живёт 15 минут и не переживает
  перезагрузку.
* **CSRF** (чужой сайт отправляет запрос от имени пользователя, браузер сам прикладывает
  cookie). Защита:
  * access-токен не cookie, а заголовок — чужой сайт его не подставит;
  * refresh-cookie с `SameSite=Strict` — браузер не отправит её с запросом, пришедшим с
    чужого сайта;
  * `Path=/api/auth` — cookie не уходит даже на остальные пути API.

После перезагрузки страницы access-токена нет → `App.jsx` при старте вызывает
`refreshSession()` и по cookie получает новый. Пользователь остаётся залогиненным.

### 3.10. Автоматическое продление на клиенте (`api.js`)

```
запрос → 401 → refreshSession() → повтор запроса с новым ключом
                      │ не удалось
                      └→ onSessionLost() → экран входа «Сессия завершена»
```

**Single-flight**: если 5 запросов одновременно получили 401, `refreshSession` возвращает
**один общий промис** (`refreshPromise`) — уходит один refresh, а не пять (иначе сработала бы
защита от повторного использования). Аналог в .NET — `DelegatingHandler` с `SemaphoreSlim`.

Скачивание вложения тоже пришлось переделать: обычная ссылка `<a href>` не приложит заголовок
`Authorization`, поэтому файл забирается через `fetch` и отдаётся как `Blob`
(`api.downloadAttachment`).

### 3.11. Хранение паролей

* Пароль **никогда не хранится** — только хеш. Хеш — **scrypt** (`crypto.scrypt`, встроен в Node).
* Почему не SHA-256: SHA очень быстрый — видеокарта перебирает миллиарды вариантов в секунду.
  scrypt специально **медленный и требует много памяти** (N=2¹⁵, r=8 → ~32 МБ на проверку), что
  делает перебор дорогим. Альтернативы того же класса — bcrypt, Argon2, PBKDF2
  (ASP.NET Identity использует PBKDF2).
* **Соль** — 16 случайных байт на каждый пароль: одинаковые пароли дают разные хеши, радужные
  таблицы бесполезны.
* Формат: `scrypt$N$r$p$соль$хеш` — параметры лежат в самом хеше, их можно усилить, не ломая
  старые пароли.
* Сравнение через `crypto.timingSafeEqual` — **за постоянное время**. Обычное `===` выходит на
  первом несовпавшем байте, и по времени ответа теоретически можно подбирать хеш побайтово
  (timing attack).
* Политика паролей (`checkPasswordPolicy`): 8–128 символов, буквы и цифры.

Секреты refresh-токенов и ссылок сброса хешируются **SHA-256**, а не scrypt: это 32 случайных
байта (256 бит энтропии), перебирать их бессмысленно, медленный хеш не нужен.

### 3.12. Первый администратор

Роль при регистрации всегда `user` (поле `role` в теле регистрации → 400 «неизвестное поле»),
иначе любой зарегистрировался бы админом. Первый админ создаётся при старте из переменных
`ADMIN_EMAIL`/`ADMIN_PASSWORD` (`authService.ensureAdmin`), дальше он назначает роли.
Админ не может разжаловать или заблокировать сам себя (409) — чтобы система не осталась без
администратора.

## 4. Пункт 2 — ошибки и коды возврата по семантике HTTP

### 4.1. Классы кодов

| Класс | Смысл | Кто виноват |
|---|---|---|
| 2xx | успех | |
| 3xx | перенаправление | |
| 4xx | ошибка **клиента**: повторять тот же запрос бессмысленно | клиент |
| 5xx | ошибка **сервера**: запрос мог быть правильным | сервер |

Главное правило: **500 — только на действительно непредвиденную ошибку**. Всё, что мы можем
предвидеть (неверные данные, нет прав, нет ресурса, лимит), — это 4xx с понятным текстом.

### 4.2. Какие коды и когда (и почему именно такие)

| Код | Когда у нас | Почему этот код |
|---|---|---|
| **200 OK** | чтение, изменение | есть тело с результатом |
| **201 Created** + `Location` | создание задачи, регистрация | создан ресурс, `Location` — его адрес |
| **202 Accepted** | «забыли пароль» | запрос принят, результат (письмо) будет позже и не раскрывается |
| **204 No Content** | удаление, выход, сброс пароля, OPTIONS | успех, тело не нужно |
| **400 Bad Request** | битый JSON, неизвестные поля, не тот тип, кривой UUID, неверный `sort` | запрос **собран неправильно** |
| **401 Unauthorized** + `WWW-Authenticate` | нет ключа, ключ истёк/подделан, сессия закрыта, неверный пароль | клиент не аутентифицирован |
| **403 Forbidden** | нет права; учётная запись заблокирована | клиент известен, но нельзя |
| **404 Not Found** | нет ресурса или он недоступен | |
| **405 Method Not Allowed** + `Allow` | `PUT /api/tasks` | ресурс есть, метод к нему неприменим |
| **409 Conflict** | email занят; админ блокирует сам себя | противоречит текущему состоянию |
| **413 Content Too Large** | файл > 10 МБ, > 5 файлов, JSON > 256 КБ | тело слишком большое |
| **415 Unsupported Media Type** | тело не JSON / multipart | формат не поддерживается |
| **422 Unprocessable Content** | пустое название, слабый пароль, дата 2026-02-31 | формат верный, **значения** не проходят |
| **429 Too Many Requests** + `Retry-After` | блокировка входа, лимит частоты | «слишком часто, повтори через N секунд» |
| **500 Internal Server Error** | непредвиденное исключение | |
| **503 Service Unavailable** + `Retry-After` | БД недоступна | временно, стоит повторить |

### 4.3. Тонкие места, о которых спросят

* **400 vs 422.** 400 — запрос собран сломанным клиентом-программой (прислали число вместо
  строки, лишнее поле, битый JSON). 422 — запрос собран правильно, но **человек** ввёл
  неподходящие значения; в теле есть `fields` — ошибки показываются под полями формы.
* **401 vs 403.** 401 — «я не знаю, кто ты» (ключа нет или он плохой) — клиенту надо войти или
  обновить ключ. 403 — «я знаю, кто ты, но тебе нельзя» — повторный вход не поможет.
  По RFC 7235 ответ 401 **обязан** содержать `WWW-Authenticate`; у нас
  `Bearer realm="api"` или `Bearer realm="api", error="invalid_token"` (формат RFC 6750).
* **405 обязан содержать `Allow`** — список разрешённых методов (RFC 9110). Делается функцией
  `methodNotAllowed(...)` в `middleware/errors.js`, которая вешается через
  `router.route(path).get(…).post(…).all(methodNotAllowed('GET','POST'))`. На `OPTIONS` та же
  функция отвечает 204 со списком методов. `HEAD` добавляется автоматически — Express обслуживает
  его для каждого GET.
* **429 и 503 содержат `Retry-After`** (секунды), клиент по нему показывает обратный отсчёт.
  Лимитер дополнительно отдаёт `RateLimit-Limit/Remaining/Reset` (черновик IETF).
* **Неверный пароль — 401, а не 400/403**: аутентификация не удалась.
* **Заблокированный админом — 403**, и только после верного пароля (см. §5.2).

### 4.4. Формат ошибок — RFC 9457 «Problem Details for HTTP APIs»

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json
X-Request-Id: 4c1b8e0f…

{
  "type": "about:blank",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "Проверьте заполнение полей задачи",
  "instance": "/api/tasks",
  "code": "validation_failed",
  "fields": { "title": "Введите название задачи" },
  "requestId": "4c1b8e0f…"
}
```

| Поле | Откуда | Смысл |
|---|---|---|
| `type` | стандарт | URI типа ошибки; `about:blank` = «смысл полностью передаёт HTTP-код» |
| `title` | стандарт | стандартная фраза кода |
| `status` | стандарт | HTTP-код (дубль, чтобы тело было самодостаточным) |
| `detail` | стандарт | объяснение для человека |
| `instance` | стандарт | на какой запрос пришла ошибка |
| `code` | расширение | машиночитаемый код: `invalid_credentials`, `account_locked`, `token_expired`… Клиент ветвится по нему, а не по тексту |
| `fields` | расширение | ошибки по полям формы |
| `requestId` | расширение | id запроса для поиска в журнале |

RFC 9457 заменил RFC 7807. В ASP.NET Core это **встроено**: `ProblemDetails`,
`ValidationProblemDetails`, `AddProblemDetails()` — мы сделали то же самое руками.

### 4.5. Как устроено в коде

1. Код бросает `HttpError` через фабрики: `HttpError.unprocessable(msg, fields)`,
   `HttpError.unauthorized(...)` (сразу с `WWW-Authenticate`), `HttpError.tooManyRequests(msg, sec)`
   (сразу с `Retry-After`) и т.д. — `lib/httpError.js`.
2. `asyncHandler` доставляет ошибку из async-обработчика в Express (Express 4 сам не ловит
   отказы промисов).
3. `errorHandler` → `normalize(error)` превращает **любую** ошибку в `HttpError`:
   * `MulterError` → 413 (лимиты) или 400;
   * ошибки body-parser: `entity.parse.failed` → 400, `entity.too.large` → 413;
   * Postgres `23505` (нарушение уникальности) → 409;
   * Postgres недоступен (`ECONNREFUSED`, `57P01`…) → 503;
   * всё остальное → 500 с общим текстом; **полный стек — только в журнал**, клиенту детали
     не показываются (иначе утечка внутренностей).
4. `sendProblem` выставляет заголовки и отдаёт `application/problem+json`.
5. Клиент (`api.js → toApiError`) превращает ответ в `ApiError { status, code, fields,
   retryAfter, requestId }`. Для 5xx к тексту дописывается «код обращения: …».

## 5. Пункт 3 — защита от подбора, контроль подключений, восстановление по email

### 5.1. От чего защищаемся

| Атака | Суть | Наша мера |
|---|---|---|
| **Brute force** | перебор паролей к одной учётке | блокировка учётки после 5 неудач на 15 мин |
| **Password spraying** | один популярный пароль (`Qwerty123`) по тысячам учёток — на каждую 1–2 попытки, блокировка не срабатывает | лимит 20 неудач за 15 мин **с одного IP** по любым email |
| **Credential stuffing** | пары логин/пароль из чужих утечек | те же лимиты + уведомление владельцу письмом |
| **Флуд эндпоинтов** | засыпать сервер запросами, заспамить ящик письмами сброса | общий rate limit на auth (100/15 мин с IP) и строгий на «забыли пароль» (5/15 мин) |
| **User enumeration** | узнать, какие email зарегистрированы | одинаковые ответы и одинаковое время (см. ниже) |
| **Timing attack** | угадывать по времени ответа | хеш-пустышка, `timingSafeEqual` |

### 5.2. Блокировка учётной записи (account lockout)

Каждая попытка входа пишется в таблицу `login_attempts (email, ip, success, reason, created_at)`.
Перед проверкой пароля `authService.assertNotThrottled`:

1. считает **неудачи с этого IP** за 15 минут → ≥ 20 → **429** `too_many_attempts`;
2. считает **неудачи по этому email** за 15 минут **после последнего успеха** → ≥ 5 и последняя
   была меньше 15 минут назад → **429** `account_locked` + `Retry-After`.

Счётчик **обнуляется** успешным входом, сбросом пароля или администратором («Разблокировать
вход» → `DELETE /api/users/:id/lock`) — все три просто добавляют строку с `success = true`.

Когда счётчик доходит до порога, владельцу уходит письмо «вход заблокирован, если это не вы —
смените пароль». В ответе на каждую неудачу — «Осталось попыток: N».

Аналог в .NET Identity: `AccessFailedCount`, `LockoutEnd`, `MaxFailedAccessAttempts = 5`,
`DefaultLockoutTimeSpan = 15 min`.

**Почему в БД, а не в памяти:** счётчик переживает перезапуск API, и попытки остаются для разбора
инцидентов. Записи старше 30 дней API удаляет сам раз в час (`server.js → purgeStaleRecords`).

**Минус блокировки и как смягчён:** злоумышленник может специально заблокировать чужую учётку
(DoS). Поэтому блокировка **временная** (15 мин), её снимает сброс пароля по email и
администратор.

### 5.3. Не раскрываем, кто зарегистрирован (anti-enumeration)

* Неверный пароль и несуществующий email → **одинаковый** 401 `invalid_credentials`.
* Счётчик неудач ведётся **по email, а не по пользователю** — несуществующий email блокируется
  точно так же (есть тест «несуществующий email блокируется так же, как существующий»).
* Если пользователя нет, пароль всё равно сверяется с **хешем-пустышкой** (`dummyHash()`), иначе
  ответ для несуществующего email пришёл бы на ~50 мс быстрее и выдал бы его.
* «Блокировка администратором» (403) сообщается **только после верного пароля**.
* «Забыли пароль» отвечает **одинаково** (202) для любого адреса, а письмо шлётся в фоне — время
  ответа тоже одинаковое.

Честное ограничение: регистрация отвечает 409 «email занят» — это неизбежно для удобства
пользователя, от массовой проверки защищает rate limit.

### 5.4. Rate limiting (`middleware/rateLimit.js`)

Алгоритм **fixed window** (фиксированное окно): для ключа `имя:IP` хранится
`{ count, resetAt }`; в новом окне счётчик сбрасывается; превысил `max` → 429 + `Retry-After`.
Хранится в `Map` в памяти процесса, истёкшие окна периодически вычищаются
(`setInterval(...).unref()` — таймер не держит процесс живым).

Другие алгоритмы, которые стоит назвать: sliding window, token bucket, leaky bucket. Fixed window
прост, но на стыке окон допускает до 2×max запросов. Для одного экземпляра API памяти
достаточно; при нескольких экземплярах счётчики переносят в Redis. В .NET —
`System.Threading.RateLimiting` (`FixedWindowRateLimiter`, `TokenBucketRateLimiter`).

**`trust proxy`.** За nginx все запросы приходят с IP nginx. Настройка
`app.set('trust proxy', 'loopback, linklocal, uniquelocal')` говорит Express брать реальный IP из
`X-Forwarded-For`, но **только если** запрос пришёл от доверенной (внутренней) сети. Без этого
все пользователи делили бы один лимит, а если доверять заголовку всегда — злоумышленник подделал
бы IP. Аналог: `UseForwardedHeaders` + `KnownNetworks`.

### 5.5. Контроль активных подключений

**Сессия** = один вход с одного устройства. Таблица `sessions`: `user_id`, `ip`, `user_agent`,
`created_at`, `last_seen_at`, `expires_at`, `revoked_at`, `revoke_reason`, хеши refresh-токена.

* **Список**: `GET /api/auth/sessions` — раздел «Безопасность», текущая помечена.
* **Завершение**: одной (`DELETE /api/auth/sessions/:id`), всех кроме текущей
  (`DELETE /api/auth/sessions`), всех у другого пользователя — админом
  (`DELETE /api/users/:id/sessions`). Чужую сессию пользователь «не видит» — 404.
* **Лимит**: не больше 5 одновременных сессий (`MAX_SESSIONS_PER_USER`). При 6-м входе
  закрывается та, что дольше всех не использовалась (`revoke_reason = 'session_limit'`).
* **Защита лимита от гонки**: вход выполняется в транзакции с `SELECT … FROM users … FOR UPDATE`
  — параллельные входы одного пользователя выстраиваются в очередь, и лимит нельзя обойти,
  отправив 10 логинов одновременно (в .NET — `IsolationLevel`/`lock` на уровне БД).
* **Отзыв мгновенный** — благодаря проверке сессии в `authenticate` (§3.7).
* **`last_seen_at`** обновляется не чаще раза в минуту — чтобы не писать в БД на каждый запрос.
* **Автоматические отзывы**: блокировка пользователя → все сессии; смена пароля → все, кроме
  текущей; сброс пароля по email → все; повтор refresh-токена → эта сессия.
* Закрытые сессии не удаляются сразу: `revoked_at` + `revoke_reason` (`logout`, `session_limit`,
  `refresh_reuse`, `password_reset`, `admin_revoked`, `user_disabled`…) нужны для расследований.

### 5.6. Восстановление доступа через email

```
1. «Забыли пароль?» → POST /api/auth/password/forgot {email}
     сервер: если пользователь есть и активен —
        secret = 32 случайных байта
        в password_resets кладём SHA-256(secret), expires_at = now()+30 мин;
        прежние неиспользованные ссылки гасятся
        письмо со ссылкой  http://localhost:8089/reset-password?token=<secret>  (в фоне)
     ответ всегда: 202 «Если такой email зарегистрирован, письмо отправлено»
2. Пользователь открывает ссылку → SPA показывает форму «Новый пароль»
3. POST /api/auth/password/reset {token, password}
     в одной транзакции:
        UPDATE password_resets SET used_at = now()
         WHERE token_hash = SHA-256(token) AND used_at IS NULL AND expires_at > now()  ← одноразовость
        новый хеш пароля
        отзыв ВСЕХ сессий пользователя
     + строка success в login_attempts → снятие блокировки входа
     ответ: 204; недействительная/истёкшая/использованная ссылка → 400 invalid_reset_token
```

Свойства, которые стоит проговорить:

* **Токен случайный и длинный** (256 бит) — угадать невозможно.
* **В БД только хеш** — утечка таблицы не даёт рабочих ссылок.
* **Срок жизни** 30 минут, **одноразовый**; «гасится» атомарным `UPDATE … WHERE used_at IS NULL` —
  даже два одновременных запроса с одной ссылкой не сработают оба.
* **Новый запрос отменяет старые ссылки.**
* **Все сессии закрываются**: если пароль украли, злоумышленник теряет доступ.
* **Письмо отправляется в фоне** (`sendMailInBackground`): ответ не ждёт SMTP и не выдаёт по
  времени, существует ли адрес; ошибка отправки попадает в журнал (`mail.failed`).
* nginx на любой путь отдаёт `index.html` (`try_files`), поэтому адрес `/reset-password?token=…`
  из письма открывается напрямую, а `lib/router.js` показывает нужный экран.
* Отправка — **nodemailer** по SMTP; в Docker — в Mailpit; в тестах —
  `MAIL_TRANSPORT=memory`: письма складываются в массив `outbox`, тест достаёт из него ссылку.

Аналог в .NET Identity: `GeneratePasswordResetTokenAsync` / `ResetPasswordAsync`.

## 6. Пункт 4 — структурированное логирование

### 6.1. Зачем «структурированное»

Обычный лог — строки текста: `User 5 logged in from 1.2.3.4`. Искать по нему можно только grep-ом
и регулярками. **Структурированный** лог — каждая запись это объект с полями:

```json
{"level":"warn","time":"2026-09-25T11:07:12.589Z","service":"spp-lab3-api","env":"production",
 "reqId":"166ce340…","event":"auth.login.failed","email":"student@example.com",
 "ip":"172.28.0.1","failures":3,"msg":"auth.login.failed"}
```

Такие записи системы сбора логов (ELK/OpenSearch, Grafana Loki, Datadog) индексируют по полям:
«все `auth.login.failed` с одного `ip` за час», «все записи запроса `reqId=…`», алерт «больше 100
`auth.account.locked` за 5 минут». Аналог в .NET — **Serilog** с `{@Object}` и JSON-синком
или `ILogger` со scopes и JSON-консолью.

### 6.2. Как сделано

* **pino** — самый быстрый JSON-логгер для Node. Настройка в `lib/logger.js`:
  * `level` из `LOG_LEVEL` (`trace < debug < info < warn < error < fatal`, `silent` в тестах);
  * базовые поля в каждой записи: `service`, `env`;
  * `time` в ISO 8601, `level` строкой (`"warn"`, а не `40`);
  * **`redact`** — маскирование секретов: заголовки `Authorization`, `Cookie`, `Set-Cookie`,
    поля `password`, `token`, `accessToken`, `refreshToken` → `[REDACTED]`. Пароли и токены
    **никогда** не попадают в журнал.
* Пишем в **stdout** — принцип *12-factor app*: приложение не управляет файлами логов, их
  собирает окружение (`docker compose logs api`, агент сборщика).
* **pino-http** (`middleware/requestLogger.js`) — одна запись на каждый завершённый запрос:
  метод, url, статус, `responseTime`, ip, user-agent, `userId`. Уровень по результату:
  2xx/3xx → `info`, 4xx → `warn`, 5xx → `error`. `/api/health` не логируется (дёргается каждые
  10 секунд — шум).
* **`req.log`** — дочерний логгер с `reqId` (а после `authenticate` — ещё `userId`, `sessionId`):
  любая запись внутри обработчика автоматически помечена, к какому запросу она относится.
* **События безопасности** — `securityEvent(log, 'auth.login.failed', {...})`: машиночитаемое имя
  события в поле `event`. Список: `auth.register`, `auth.login.success/failed/disabled/
  locked_attempt/ip_blocked`, `auth.account.locked`, `auth.refresh.reuse_detected`,
  `auth.session.evicted/revoked/revoked_others`, `auth.logout`, `auth.password_reset.requested/
  completed`, `auth.password_change.completed/failed`, `users.updated/unlocked/sessions.revoked`,
  `access.denied`, `rate_limit.exceeded`, `mail.sent/failed`, `task.created/updated/deleted`.
  Это одновременно **журнал аудита**: кто, что, когда, с какого IP.
* **Ошибки 5xx** пишутся с полным стеком (`err`), клиенту уходит только общий текст и `requestId`.
* ESLint-правило **`no-console: error`** — нельзя случайно вернуть неструктурированный
  `console.log`.

### 6.3. Сквозной идентификатор запроса (correlation id)

```
nginx: $request_id = 166ce340…  →  пишет в свой JSON-лог
       proxy_set_header X-Request-Id $request_id
api:   берёт X-Request-Id (если похож на безопасный токен, иначе генерирует UUID)
       → во все свои записи этого запроса (reqId)
       → в заголовок ответа X-Request-Id
       → в тело ошибки requestId
клиент: при 5xx показывает «код обращения: 166ce340…»
```

Пользователь присылает код из сообщения об ошибке → по нему за секунды находятся запись nginx,
все записи API и стек ошибки. Входящий `X-Request-Id` проверяется регулярным выражением —
иначе через заголовок можно было бы внедрить в журнал что угодно (log injection).
В .NET это `HttpContext.TraceIdentifier` / `Activity.TraceId` (W3C Trace Context).

nginx тоже пишет access-лог в JSON (`log_format json_combined escape=json` в `nginx.conf`).

## 7. Пункт 5 — автоматизированная проверка кода (CI)

### 7.1. Что такое CI

**Continuous Integration** — каждое изменение кода автоматически проверяется: собирается,
прогоняется линтером и тестами. Ошибка находится в момент push, а не на защите.
Ключевая идея — проверка **автоматическая и одинаковая для всех** (в «чистой» машине, а не
«у меня работает»).

### 7.2. GitHub Actions — термины

| Термин | Что это | У нас |
|---|---|---|
| **workflow** | YAML-файл с описанием пайплайна в `.github/workflows/` | `lab3.yml` |
| **trigger (`on`)** | когда запускать | `push` и `pull_request` с изменениями в `Lab3/**`, ручной `workflow_dispatch` |
| **job** | набор шагов на одной виртуальной машине; jobs идут параллельно | `server`, `client`, `docker`, `audit` |
| **step** | одна команда или готовое действие (`uses:`) | `npm ci`, `npm run lint`, `npm test` |
| **runner** | машина, где выполняется job | `ubuntu-latest` |
| **service container** | вспомогательный контейнер на время job | PostgreSQL 16 для тестов |
| **needs** | зависимость между jobs | `docker` запускается, только если `server` и `client` зелёные |
| **matrix** | один job для нескольких значений | `audit` для `server` и `client` |
| **concurrency** | отмена устаревших прогонов | новый push в ветку отменяет прежний прогон |
| **cache** | кэш зависимостей | `actions/setup-node` кэширует npm по `package-lock.json` |

Аналог — Azure DevOps Pipelines / GitHub Actions с `dotnet build`, `dotnet test`.

Файл лежит в **корне** репозитория, а не в `Lab3/`: GitHub ищет workflows только в
`.github/workflows` корня. Фильтр `paths` запускает его только при изменениях Lab3.

### 7.3. Что проверяется

| Job | Шаги | Что ловит |
|---|---|---|
| `server` | `npm ci` → `npm run lint` → `npm test` | ошибки стиля и потенциальные баги; регрессии в логике доступа |
| `client` | `npm ci` → `npm run lint` → `npm run build` | нарушения правил React Hooks, ошибки импорта, несобираемый бандл |
| `docker` | `docker compose config` → `docker compose build` | сломанный compose-файл или Dockerfile |
| `audit` | `npm audit --omit=dev --audit-level=high` | известные уязвимости в production-зависимостях |

* **`npm ci`, а не `npm install`**: ставит ровно то, что в `package-lock.json`, и падает при
  рассинхроне — воспроизводимая сборка (как `dotnet restore --locked-mode`).
* **ESLint** — статический анализатор (аналог Roslyn-анализаторов / StyleCop). У нас: базовые
  правила `recommended`, `eqeqeq`, `prefer-const`, `no-console`; на клиенте — правила React и
  `react-hooks/rules-of-hooks`.
* Чтобы красный CI **блокировал слияние**, в настройках GitHub включается *Branch protection
  rule* для `main` с обязательными проверками.

### 7.4. Автотесты (46 штук)

* Раннер — встроенный **`node:test`** (аналог xUnit), проверки — `node:assert`.
* **supertest** гоняет запросы прямо в Express-приложение без поднятия порта
  (аналог `WebApplicationFactory` + `HttpClient` в ASP.NET Core).
* **Модульные** (`unit.test.js`, без БД): хеш пароля, политика паролей, матрица прав ролей,
  подпись/проверка JWT, разбор refresh-токена, заголовки `HttpError`, валидация тел.
* **Интеграционные** (`auth.test.js`, `access.test.js`) — на **настоящем PostgreSQL**: перед
  каждым тестом `TRUNCATE` всех таблиц, `helpers.createUser(role)` создаёт пользователя и
  логинится. Проверяют сценарии целиком: блокировка после неудач с 429 и письмом, ротация и
  кража refresh-токена, лимит сессий, полный цикл сброса пароля по письму, изоляция задач между
  пользователями, 403 менеджеру на удаление чужой, 405 + `Allow`, формат problem+json и т.д.
* Тестам подменяется окружение (`NODE_ENV=test`, лимиты поменьше, почта в память), а время
  «проматывается» прямо в БД (`UPDATE … SET rotated_at = now() - interval '1 hour'`), чтобы не
  ждать реальные 30 секунд или 30 минут.
* Файлы тестов идут последовательно (`--test-concurrency=1`) — они делят одну БД.

### 7.5. Локальный pre-commit-хук

`.githooks/pre-commit` перед каждым коммитом прогоняет ESLint по той части Lab3 (server или
client), в которой есть изменённые JS-файлы. Включается один раз:
`git config core.hooksPath .githooks`. Это «CI на своей машине» — ошибка ловится ещё до push.

## 8. Схема базы данных (что добавилось)

```
users            id, email UNIQUE (в нижнем регистре, CHECK), name, password_hash,
                 role CHECK IN ('user','manager','admin'), is_active,
                 created_at, updated_at, password_changed_at
sessions         id, user_id → users ON DELETE CASCADE,
                 refresh_hash, prev_refresh_hash, rotated_at,
                 ip, user_agent, created_at, last_seen_at, expires_at,
                 revoked_at, revoke_reason
                 индекс по user_id WHERE revoked_at IS NULL (частичный — только активные)
login_attempts   id, email, ip, success, reason, created_at
                 индексы (email, created_at DESC), (ip, created_at DESC)
password_resets  id, user_id → users, token_hash UNIQUE, expires_at, used_at, created_at
tasks            + owner_id → users ON DELETE CASCADE  (+ индекс)
```

Роли и email проверяются ещё и `CHECK`-ограничениями — данные корректны, даже если писать в БД
в обход API. Все запросы параметризованы (`$1, $2`) — SQL-инъекции исключены.

## 9. Сценарий демонстрации на защите

1. `cd Lab3 && docker compose up --build`, открыть <http://localhost:8089>.
2. **Роли.** Зарегистрировать двух пользователей (например, в обычном и приватном окне), каждый
   создаёт задачу → каждый видит только свою. Войти админом `admin@example.com / Admin12345` →
   видны обе задачи с владельцами; в «Пользователях» назначить одному роль «Менеджер» → у него
   сразу (без перезахода) появятся чужие задачи и пропадёт кнопка «Удалить» на них.
3. **Коды HTTP** (терминал):
   ```bash
   curl -i http://localhost:3003/api/tasks                  # 401 + WWW-Authenticate
   curl -i -X PUT http://localhost:3003/api/tasks           # 401 (сначала вход), с токеном — 405 + Allow
   curl -i -X POST http://localhost:3003/api/auth/login \
        -H 'Content-Type: application/json' -d '{"email":"x"}'   # 422 + fields
   ```
   Показать `Content-Type: application/problem+json` и `requestId`.
4. **Подбор пароля.** 5 раз ввести неверный пароль → «Осталось попыток: …», затем 429 и кнопка
   с обратным отсчётом; в Mailpit (<http://localhost:8026>) — письмо о блокировке; в
   «Пользователях» у админа — «Вход закрыт до …» и кнопка «Разблокировать вход».
5. **Сессии.** Войти одним пользователем из двух браузеров → в «Безопасности» две сессии, завершить
   вторую → во втором браузере при следующем действии выкинет на экран входа.
6. **Восстановление.** «Забыли пароль?» → письмо в Mailpit → перейти по ссылке → новый пароль →
   все сессии закрыты, повторно ссылка не работает.
7. **Логи.** `docker compose logs api | grep '"event"'` — события безопасности;
   `docker compose logs web` — JSON nginx с тем же `reqId`.
8. **CI.** Открыть вкладку *Actions* на GitHub → прогон с четырьмя зелёными jobs; локально —
   `cd server && npm run lint && npm test`.

## 10. Вопросы, которые могут задать, и короткие ответы

**Почему не хранить JWT в `localStorage`?** Его прочитает любой XSS-скрипт. Access в памяти
живёт 15 минут, refresh в HttpOnly-cookie JavaScript недоступен вовсе.

**Чем JWT лучше обычной сессии с cookie?** Сам по себе — не проверять БД на каждый запрос
(stateless). Мы сознательно добавили проверку сессии, чтобы получить мгновенный отзыв и
контроль подключений; JWT остаётся стандартным переносимым форматом ключа с подписью и сроком.

**Что будет, если украдут access-токен?** Максимум 15 минут доступа; раньше — если пользователь
завершит сессию или сменит пароль. **А refresh-токен?** При первом же обновлении кем-то из двух
второй предъявит уже использованный токен → сессия закроется целиком.

**Зачем два хеша в `sessions` (`refresh_hash`, `prev_refresh_hash`)?** Чтобы отличить законную
гонку двух вкладок (предыдущий токен в течение 30 секунд) от кражи.

**Почему scrypt, а не SHA-256 для паролей?** SHA быстрый — его выгодно перебирать; scrypt
медленный и ест память. Соль делает одинаковые пароли разными хешами.

**Почему на чужую задачу 404, а не 403?** Чтобы не раскрывать её существование.

**Чем 400 отличается от 422?** 400 — запрос сломан (формат, типы, лишние поля), 422 — формат
верный, но значения не прошли проверку (ошибки по полям).

**Чем 401 отличается от 403?** 401 — «не знаю, кто ты», поможет вход/обновление ключа.
403 — «знаю, но нельзя», повторный вход не поможет.

**Почему блокировка по email, а не по пользователю?** Чтобы несуществующий email вёл себя так же
— иначе по блокировке можно было бы узнать, кто зарегистрирован.

**Зачем ещё и лимит по IP?** Против password spraying: один пароль по многим учёткам,
на каждую меньше 5 попыток — блокировка учётки не сработает, а лимит IP сработает.

**Почему «забыли пароль» отвечает 202 и одинаково?** Результат асинхронный (письмо), и ответ не
должен выдавать, зарегистрирован ли адрес.

**Как злоумышленник может использовать блокировку во вред и что с этим?** Специально блокировать
чужую учётку. Блокировка временная, снимается сбросом пароля и администратором.

**Что будет с rate limit, если запустить 3 экземпляра API?** У каждого свои счётчики в памяти —
лимит фактически ×3. Решение — общее хранилище (Redis). Блокировка входа хранится в БД и от
числа экземпляров не зависит.

**Что даёт структурированный лог по сравнению с `console.log`?** Поиск и агрегация по полям,
алерты, корреляция запроса через `reqId`, гарантированное маскирование секретов.

**Что такое `reqId` и откуда он берётся?** Генерирует nginx (`$request_id`), передаёт в API в
`X-Request-Id`; API пишет его во все записи запроса и возвращает клиенту.

**Что делает CI и когда запускается?** На каждый push/PR, затрагивающий Lab3: ESLint, 46 тестов
на настоящем PostgreSQL, сборка SPA и Docker-образов, аудит зависимостей.

**Чем интеграционный тест отличается от модульного?** Модульный проверяет функцию в изоляции
(хеш пароля, матрица прав). Интеграционный — весь путь HTTP-запрос → middleware → БД → ответ.
