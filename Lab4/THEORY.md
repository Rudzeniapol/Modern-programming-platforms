# Теория к лабораторной работе №4 — «Пиксельная битва»
### Как всё устроено: что где лежит, как ходят сообщения, где и как хранятся данные

**Как читать.** Разделы 1–4 дают общую картину и объясняют, где живут данные. Без них
остальное не сложится. Разделы 5–7 описывают связь клиента с сервером и путь одного хода от
клика до экранов всех игроков. Разделы 8–9 — дополнительные требования: конфликты и обрыв связи.
Дальше идут игровая логика, отрисовка, HTTP, безопасность, логи, тесты, развёртывание, сценарий
демонстрации и вопросы на защите. В конце есть словарь терминов.

Для тех, кто знает C#/.NET: ближайший аналог того, что здесь сделано руками, — **ASP.NET Core
SignalR** (хаб, рассылка всем, автоматическое переподключение). У нас нет SignalR: есть «голый»
протокол WebSocket и собственный протокол сообщений поверх него.

## 0. Коротко

«Пиксельная битва» — игра в духе r/place. Четыре команды закрашивают клетки общего поля
64×40. Раунд длится 10 минут, и побеждает команда, у которой к концу больше клеток. Потом поле
очищается и начинается новый раунд. Темп ограничен **зарядами**: подряд можно закрасить не больше
10 клеток, а дальше заряды восстанавливаются по одному каждые 3 секунды.

На всём проекте держатся пять идей:

1. **Сервер авторитетен.** Клиент только *просит* закрасить клетку, решение принимает сервер.
2. **Данные живут в трёх местах.** PostgreSQL — источник истины. Память сервера — быстрая копия
   поля. Браузер — своя копия плюс очередь ещё не подтверждённых ходов. Изменение всегда
   идёт в одном порядке: **сначала БД, потом память сервера, потом все клиенты**.
3. **Связь — один WebSocket на вкладку**, по нему ходят JSON-сообщения `{ type, … }`.
4. **Конфликты** одновременного изменения решает **версия клетки**: ход принимается, только если
   клетка не изменилась с того момента, как игрок её увидел.
5. **Обрывы связи** переживаются за счёт трёх механизмов: состояние лежит в `localStorage`;
   после переподключения клиент получает только пропущенное (по номеру `seq`); ходы
   досылаются без дублей (по `actionId`).

**Фраза для защиты:** «Сервер авторитетен: клиент шлёт намерения, сервер решает. Синхронизация —
WebSocket с рассылкой изменений. Конфликты решаются оптимистической блокировкой по версии клетки,
политика first-write-wins. Офлайн-режим — локальное сохранение, очередь ходов с идемпотентными
`actionId` и дельта-синхронизация по порядковому номеру изменений из журнала ходов. Всё состояние
хранится в PostgreSQL и переживает перезапуск».

## 1. Общая картина

### 1.1. Из чего состоит система

```
                 БРАУЗЕР (вкладка)                                   СЕРВЕР (один процесс Node.js)
┌──────────────────────────────────────────┐               ┌──────────────────────────────────────────────┐
│ main.js — связывает всё                  │  HTTP GET     │ http/app.js    маршруты /api/*, заголовки     │
│ connection.js — WebSocket + переподключ. │──────────────►│ http/static.js раздача файлов из public/      │
│ state.js — копия поля, очередь ходов ────┼─► localStorage│                                              │
│ renderer.js — рисует поле на <canvas>    │  WebSocket /ws│ ws/hub.js      подключения, разбор сообщений, │
│ ui.js — всё остальное на странице        │◄═════════════►│                рассылка всем                  │
└──────────────────────────────────────────┘  JSON-сообщ.  │ game/Game.js   правила игры, поле в памяти,   │
                                                           │                очередь ходов, раунды          │
                                                           │ game/repository.js   весь SQL                 │
                                                           └───────────────────────┬──────────────────────┘
                                                                                   │ драйвер pg
                                                           ┌───────────────────────▼──────────────────────┐
                                                           │ PostgreSQL: players, rounds, cells, moves     │
                                                           │ (файлы БД — в Docker-томе pgdata)             │
                                                           └──────────────────────────────────────────────┘
```

* `docker compose up` поднимает **два контейнера**: `db` (PostgreSQL 16) и `app` (Node.js 22).
* Наружу открыт **один порт — 8092**. На нём сервер отдаёт и страницу (обычный HTTP), и
  WebSocket (путь `/ws`). Хостинги дают приложению один порт, поэтому так удобнее всего.
* Сборщика нет: браузер получает файлы из `public/` ровно такими, какими они лежат в репозитории.

### 1.2. Три места, где живут данные

| Где | Что лежит | Зачем | Что будет, если пропадёт |
|---|---|---|---|
| **PostgreSQL** | всё: игроки, раунды, поле, журнал ходов | источник истины, переживает перезапуск | данные потеряны; поэтому БД лежит в именованном томе `pgdata` |
| **Память сервера** (`Game`) | копия поля *текущего* раунда, счёт, имена игроков, номер последнего изменения `seq` | отдавать поле и счёт мгновенно, без `SELECT` на каждое подключение | ничего страшного: при старте восстанавливается из БД (`Game.init`) |
| **Память сервера** (`Hub`) | список открытых соединений | знать, кто онлайн и кому рассылать | клиенты сами переподключатся |
| **Память вкладки** (`GameState`) | копия поля, свой игрок, очередь ходов | рисовать поле и проверять ход до отправки | восстанавливается из `localStorage` или с сервера |
| **`localStorage` браузера** | то же, что в памяти вкладки, **плюс токен игрока** | пережить перезагрузку вкладки и работу без сети | поле придёт с сервера; без токена игрок станет новым |
| **Нигде** | курсоры других игроков, список «кто онлайн» | данные эфемерные | ничего, через долю секунды придут новые |

**Главное правило:** изменение движется только в одном направлении:

```
COMMIT в PostgreSQL  ──►  обновление поля в памяти сервера  ──►  рассылка клиентам  ──►  localStorage
```

Если запись в БД не удалась, изменения не видит никто. Поэтому невозможна ситуация, когда
игроки видят клетку, которой на самом деле нет.

### 1.3. Авторитетный сервер

Клиенту **нельзя доверять**: любой может открыть DevTools и отправить в WebSocket что угодно.
Поэтому:

* клиент шлёт **намерение** («хочу закрасить (10, 5), я видел её в версии 1»);
* сервер сам проверяет всё: раунд, версию клетки, заряды. **Команду игрока сервер берёт из БД**, а
  не из сообщения, поэтому закрасить «за чужую команду» нельзя;
* сервер рассылает **результат**, и все клиенты приводят своё поле к нему.

Клиент при этом показывает ход сразу, не дожидаясь ответа (**оптимистичный интерфейс**): клетка
рисуется полупрозрачной с пунктирной рамкой. Если сервер ход отклонил, клиент откатывает его.

### 2.4. Кто кого вызывает

```
server.js ──► migrate()                          main.js ──► Connection   (connection.js)
          ──► new Game() ──► repository ──► pool         ──► GameState    (state.js) ──► localStorage
          │              ──► charges                     ──► BoardRenderer(renderer.js)
          │              ──► SerialQueue                 ──► UI           (ui.js)
          ──► createRequestHandler (http/app.js ──► static.js)
          ──► new Hub({ server, game }) ──► protocol.parseClientMessage
                         ▲    │
       события Game ─────┘    └──► game.paint(), game.createPlayer(), game.syncFor() …
       (pixel, scores, roundEnd, roundStart)
```

`Game` **ничего не знает о WebSocket**. Он только меняет состояние и генерирует события
(`EventEmitter`): `pixel`, `scores`, `roundEnd`, `roundStart`. `Hub` на них подписан и рассылает
их клиентам. Такое разделение позволяет тестировать игровую логику напрямую, а сетевую часть
менять, не трогая правила игры.

| Модуль | Аналог в .NET |
|---|---|
| `ws/hub.js` | SignalR `Hub` + `Clients.All.SendAsync` |
| `game/Game.js` | singleton-сервис с состоянием игры |
| `lib/serialQueue.js` | `SemaphoreSlim(1)` или `Channel<T>` с одним читателем |
| `game/repository.js` | репозиторий на Dapper |
| `game/protocol.js` | валидация DTO |
| `http/app.js` + `static.js` | Kestrel без MVC + `UseStaticFiles` |
| `connection.js` | `HubConnectionBuilder().WithAutomaticReconnect()` |

## 3. Запуск и остановка сервера

Что происходит после `node src/server.js` (в Docker — сразу при старте контейнера `app`):

1. **`config.js`** читает переменные окружения (`PORT`, `DATABASE_URL`, `ROUND_DURATION_SEC`, …).
2. **`migrate()`**. В docker-compose приложение может стартовать раньше, чем Postgres готов, поэтому
   `waitForDatabase()` пробует подключиться до 30 раз с паузой в секунду. Потом выполняется
   `schema.sql`. Он идемпотентен (`CREATE TABLE IF NOT EXISTS`), поэтому его можно запускать при
   каждом старте.
3. **`game.init()`** — загрузка игры из БД:
   * найти активный раунд (`finished_at IS NULL`), а если его нет — создать;
   * `seq` = наибольший номер применённого хода в журнале `moves`;
   * `loadRound()`: прочитать клетки раунда из `cells` в память, а из `moves` — кто сколько
     закрасил в этом раунде;
   * если раунд **должен был закончиться, пока сервер был выключен**, сразу подвести итоги и начать
     новый; иначе поставить таймер на `ends_at`.
4. **`http.createServer(...)`**: обработчик обычных HTTP-запросов (страница, `/api/*`).
5. **`new Hub({ server, game })`**: подписка на событие `upgrade` HTTP-сервера (переход на
   WebSocket), подписка на события игры, запуск heartbeat раз в 15 секунд.
6. **`server.listen(PORT)`**: в журнал пишется `{"event":"game.loaded","roundId":…}` и
   `{"event":"server.started","port":8092}`.

**Остановка** (`docker compose stop`, Ctrl+C → сигнал `SIGTERM`/`SIGINT`):

1. `hub.close()`: каждому клиенту уходит фрейм закрытия с кодом **1001 «Going Away»**. Клиенты
   понимают, что сервер уходит, и начинают переподключаться. Тех, кто не ответил за секунду,
   сервер обрывает принудительно.
2. `game.stop()`: таймеры раунда и счёта снимаются.
3. `await game.queue.run(() => undefined)`: ходы, уже стоящие в очереди, **успевают записаться в БД**.
4. `server.close()` и `pool.end()`: HTTP-сервер и соединения с БД закрываются.

## 4. Данные: как и где хранятся

### 4.1. PostgreSQL — схема

```
players ─┬──< cells.player_id   (ON DELETE SET NULL)
         └──< moves.player_id   (ON DELETE CASCADE)
rounds  ─┬──< cells.round_id    (ON DELETE CASCADE)
         └──< moves.round_id    (ON DELETE CASCADE)
```

Четыре таблицы, у каждой одна роль:

* `players` — **кто** играет;
* `rounds` — **когда** (раунды и их итоги);
* `cells` — **что сейчас** на поле (текущее состояние);
* `moves` — **что происходило** (журнал всех ходов).

`cells` и `moves` работают как остаток на счёте и выписка операций. Остаток показывает, что есть
сейчас, а выписка — как к этому пришли. Обе таблицы меняются **в одной транзакции**, поэтому
разойтись не могут.

#### `players` — игроки

| Столбец | Тип | Смысл |
|---|---|---|
| `id` | `UUID` PK | идентификатор игрока (`gen_random_uuid()`) |
| `token_hash` | `TEXT UNIQUE` | **SHA-256 от токена**; сам токен в БД не хранится |
| `name` | `TEXT` | имя, `CHECK (length(name) BETWEEN 2 AND 20)` |
| `team` | `SMALLINT` | команда 0–3 (индекс в `config.teams`) |
| `charges`, `charges_at` | `SMALLINT`, `TIMESTAMPTZ` | сколько зарядов было **в момент** `charges_at` (подробнее в разделе 10.1) |
| `pixels_total` | `INTEGER` | закрашено клеток за всё время |
| `created_at`, `last_seen_at` | `TIMESTAMPTZ` | когда создан и когда последний раз был в игре |

```
 id    | token_hash      | name  | team | charges | charges_at          | pixels_total
-------+-----------------+-------+------+---------+---------------------+-------------
 98a3… | f9535fbeeb65…   | Кира  |    2 |       8 | 2026-10-15 12:00:06 |           32
 c1d2… | 0b7e41a9c3d0…   | Алиса |    0 |      10 | 2026-10-15 11:58:40 |           12
```

**Почему без пароля.** Регистрация в задании не требуется. При первом входе сервер генерирует
**случайный токен из 32 байт** (`crypto.randomBytes(32)`, в base64url это 43 символа), отдаёт его
клиенту, а в БД кладёт только SHA-256 от токена. Если базу украдут, хеши не помогут войти за
игрока. Медленный хеш с солью, как для паролей, не нужен: токен случаен и содержит 256 бит, так
что подобрать его невозможно.

#### `rounds` — раунды

| Столбец | Смысл |
|---|---|
| `id` | номер раунда (`SERIAL`) |
| `started_at`, `ends_at` | начало и **плановый** конец. `ends_at` хранится в БД, поэтому таймер раунда переживает перезапуск сервера |
| `finished_at` | фактический конец; `NULL` — раунд идёт сейчас |
| `winner_team` | победитель; `NULL` — ничья |
| `scores` | `JSONB` — итоговый счёт: по каждой команде клетки к концу раунда и сколько её игроков участвовало, плюс лучшие игроки |
| `final_board` | `JSONB` — **итоговая карта**: снимок поля в момент завершения раунда (см. ниже) |

```
 id | finished_at | winner_team | scores                                            | final_board
----+-------------+-------------+---------------------------------------------------+------------------------------------------
  7 |             |             |                                                   |                               ← активный
  6 | 12:00:00    |           1 | {"teams":[{"id":0,"cells":210,"players":2},…],…}  | {"width":64,"height":40,"cells":"..0011…"}
  4 | 11:40:00    |             | {"teams":[{"id":0,"cells":305,"players":1},…],…}  | {…}   ← ничья: у двух команд поровну
```

Раунда №5 в таблице нет: в нём никто не играл, и он удалён (см. «Очистка старых данных»).

**Только один активный раунд** гарантирует сама БД:

```sql
CREATE UNIQUE INDEX rounds_single_active_idx ON rounds ((true)) WHERE finished_at IS NULL;
```

Это **частичный уникальный индекс по константе**. В индекс попадают только незаконченные раунды,
и у всех них индексируемое значение одинаковое (`true`). Поэтому вторая строка с
`finished_at IS NULL` нарушит уникальность, и `INSERT` упадёт.

`scores` и `final_board` хранятся как `JSONB`: это **неизменяемый снимок итогов** для истории.
Их не нужно ни искать, ни обновлять, поэтому раскладывать по отдельным таблицам незачем.

**Итоговая карта (`final_board`).** В момент завершения раунда поле из памяти кодируется в
строку (`Game.encodeBoard`): по символу на клетку построчно, `'0'`–`'3'` — команда, `'.'` —
пустая клетка.

```
{ "width": 64, "height": 40, "cells": "330.......…" }      ← 64 × 40 = 2560 символов
клетка (x, y) = cells[y · width + x]                         ← та же адресация, что у поля в памяти
```

* **Почему строка, а не массив `[x, y, команда]`?** 2,5 КБ на раунд, а не десятки, и одна
  строка вместо тысяч троек. Шесть карт истории спокойно помещаются в `welcome`.
* **Почему не брать карту из `cells`?** Клетки завершённого раунда тоже лежат в `cells` до
  очистки, но итоговая карта — это **снимок на момент конца раунда**. Он читается одним
  запросом вместе с итогами, и история не зависит от того, как хранится живое поле.
* **Какие команды играли** (`scores.teams[i].players`) считается по журналу ходов, а не по карте:
  ```sql
  SELECT team, COUNT(DISTINCT player_id) AS players
    FROM moves WHERE round_id = $1 AND status = 'ok' GROUP BY team
  ```
  Команда могла играть, но к концу остаться без клеток: их перекрасили соперники. По карте
  это не видно, а по журналу видно.

#### `cells` — поле

| Столбец | Смысл |
|---|---|
| `round_id, x, y` | **составной первичный ключ**: у каждого раунда своё поле |
| `team` | цвет клетки (команда) |
| `player_id` | кто закрасил последним |
| `version` | **сколько раз клетку красили в этом раунде**, `CHECK (version > 0)` |
| `updated_at` | когда |

```
 round_id | x  | y | team | player_id | version
----------+----+---+------+-----------+--------
        7 |  3 | 3 |    0 | c1d2…     |       1
        7 | 10 | 5 |    0 | c1d2…     |       2   ← клетку перекрашивали
        7 | 11 | 5 |    2 | 98a3…     |       1
```

* **Нет строки — значит, клетка пустая, версия 0.** Пустое поле — это 0 строк, а не 2560
  строк-заглушек.
* **Версия — основа защиты от конфликтов** (раздел 8). В пределах раунда она только растёт.
* **Почему каждая клетка — отдельная строка, а не всё поле одним JSON?** Так проверку версии
  можно делать по одной клетке условным `UPDATE … WHERE version = …`. Строк в раунде не больше
  2560, для PostgreSQL это ничто.
* **Почему поле привязано к раунду**, а не очищается `DELETE`? Новый раунд — это просто новый
  `round_id`, старое поле новому не мешает, а очистка делается одним каскадным удалением раунда.

#### `moves` — журнал ходов

| Столбец | Смысл |
|---|---|
| `seq` | `BIGSERIAL` PK — **глобальный порядковый номер** записи в журнале |
| `round_id`, `player_id` | чей ход и в каком раунде |
| `action_id` | `UUID` хода, **сгенерированный клиентом**; `UNIQUE (player_id, action_id)` |
| `x`, `y`, `team` | куда и каким цветом |
| `status` | `ok`, `conflict` или `no_charges` — чем закончилась обработка |
| `cell_version` | версия клетки после хода (при `ok`) или её текущая версия (при отказе) |

```
 seq | round_id | player | action_id | x  | y | team | status   | cell_version
-----+----------+--------+-----------+----+---+------+----------+-------------
 117 |        7 | Кира   | 5be1…     | 10 | 5 |    2 | ok       |            1
 118 |        7 | Алиса  | 0f4a…     |  3 | 3 |    0 | ok       |            1
 119 |        7 | Алиса  | 9c27…     | 10 | 5 |    0 | ok       |            2   ← перекрасила клетку Киры
 120 |        7 | Кира   | 71d0…     | 10 | 5 |    2 | conflict |            2   ← Кира видела версию 1
 121 |        7 | Кира   | e8b5…     | 11 | 5 |    2 | ok       |            1
```

У журнала **три роли**:

1. **Порядковый номер для дельта-синхронизации.** Клиент помнит последний известный ему `seq`.
   После переподключения сервер присылает только применённые изменения с бо́льшим номером
   (раздел 9.4).
2. **Защита от дублей.** Если клиент повторно отправит ход с тем же `actionId`, сервер найдёт
   его в журнале и вернёт прежний результат (раздел 9.5). Поэтому в журнал пишутся **и
   отклонённые ходы** (`conflict`, `no_charges`): на повтор сервер должен ответить тем же вердиктом.
3. **Статистика**: «лучшие игроки раунда» — это `COUNT(*) … WHERE status = 'ok' GROUP BY player_id`.

**Пропуски в `seq` — это нормально.** Номера берёт и отклонённый ход (в примере №120), а
откатившаяся транзакция тоже «съедает» значение последовательности. Номер нужен только для
сравнения «больше или меньше», подряд они идти не обязаны.

**Частичный индекс** под запрос дельты:

```sql
CREATE INDEX moves_round_applied_idx ON moves (round_id, seq) WHERE status = 'ok';
```

В индекс попадают только применённые ходы, поэтому он меньше и точно соответствует запросу
`WHERE round_id = $1 AND status = 'ok' AND seq > $2 ORDER BY seq`.

#### Что делает с таблицами один ход

Кира (команда 2) закрашивает пустую клетку (11, 5) в 12:00:06.000. До хода у неё 8 зарядов,
записанных в 12:00:03.000.

| Таблица | Было | Стало |
|---|---|---|
| `players` (Кира) | `charges=8, charges_at=12:00:03, pixels_total=31` | заряды: 8 + 1 восстановленный − 1 потраченный = **8**, `charges_at=12:00:06`, `pixels_total=32` |
| `cells` | строки `(7, 11, 5)` нет | **новая строка** `(7, 11, 5, team=2, player=Кира, version=1)` |
| `moves` | — | **новая строка** `seq=121, x=11, y=5, team=2, status='ok', cell_version=1` |

Всё это — одна транзакция. Только после `COMMIT` сервер меняет поле в памяти и рассылает
`pixel { seq: 121, … }` всем клиентам.

#### Очистка старых данных

После каждого раунда (и при старте сервера) выполняется `pruneRounds(10)`:

* остаются **10 последних сыгранных раундов** — тех, у которых на поле есть хоть одна клетка;
* все остальные завершённые раунды удаляются, **в том числе пустые**, в которых никто не играл;
* активный раунд не трогается.

```sql
DELETE FROM rounds
 WHERE finished_at IS NOT NULL
   AND id NOT IN (SELECT r.id FROM rounds r
                   WHERE r.finished_at IS NOT NULL
                     AND EXISTS (SELECT 1 FROM cells c WHERE c.round_id = r.id)
                   ORDER BY r.id DESC LIMIT 10)
```

Благодаря `ON DELETE CASCADE` вместе с раундом удаляются его `cells` и `moves`. Игроки не удаляются
никогда, а их `pixels_total` хранится в `players`, поэтому статистика «за всё время» не теряется.

**Зачем удалять пустые раунды.** Раунды сменяются каждые 10 минут, даже когда никто не играет.
Если бы очистка просто оставляла 10 последних раундов, то за 100 минут простоя пустые раунды
вытеснили бы из истории все сыгранные. Теперь пустой раунд удаляется в той же транзакции, в
которой завершается. Поэтому номера в истории идут с пропусками (№4, №6, №12), и это нормально.

#### Как посмотреть данные руками



### 4.2. Память сервера

**`Game`** — копия текущего раунда:

| Поле            | Тип                     | Что хранит                                                  |
| --------------- | ----------------------- | ----------------------------------------------------------- |
| `round`         | объект                  | `{ id, startedAt, endsAt, … }` активного раунда             |
| `seq`           | число                   | номер последнего **применённого** хода                      |
| `board.team`    | `Int8Array(2560)`       | цвет каждой клетки; `-1` — пустая                           |
| `board.version` | `Int32Array(2560)`      | версия каждой клетки                                        |
| `board.owner`   | `Array(2560)`           | `id` игрока, закрасившего клетку                            |
| `teamCells`     | `[n0, n1, n2, n3]`      | сколько клеток у каждой команды: счёт без пересчёта поля    |
| `roundPixels`   | `Map(playerId → число)` | сколько закрасил каждый игрок в этом раунде                 |
| `playerNames`   | `Map(playerId → имя)`   | имена для рассылок и таблицы лидеров                        |
| `queue`         | `SerialQueue`           | очередь, через которую проходят **все** изменения состояния |

**Двумерное поле хранится в одномерном массиве**: `i = y · width + x`. Например, клетке (11, 5)
соответствует `5 · 64 + 11 = 331`. **Типизированные массивы** (`Int8Array`, `Int32Array`)
компактны (2,5 КБ и 10 КБ), имеют фиксированный размер и работают быстрее обычных массивов.
`Int8Array` хватает, потому что значения −1…3 помещаются в байт.

**Кеш никогда не опережает БД.** Память меняется только после `COMMIT` и только внутри очереди.
Если копия в памяти и БД всё-таки разойдутся, побеждает БД: условная запись в БД вернёт «не
записано», и ход получит `conflict` (раздел 8.4).

**`Hub`** хранит только `clients` — множество (`Set`) открытых соединений. Для каждого соединения:

| Поле | Зачем |
|---|---|
| `ws` | само соединение (объект библиотеки `ws`) |
| `player` | игрок этого соединения или `null` (зритель) |
| `ready` | `welcome` уже отправлен, значит, рассылки можно слать |
| `alive` | ответил ли на последний ping (heartbeat) |
| `chain` | цепочка промисов: сообщения **одного** клиента обрабатываются по порядку |
| `bucket`, `violations` | ограничение частоты сообщений (token bucket) |
| `lastCursorAt` | прореживание курсоров |

### 4.3. Браузер

**`GameState`** в памяти вкладки:

| Поле | Что хранит |
|---|---|
| `token` | токен игрока, полученный при входе; по нему сервер узнаёт игрока |
| `player` | `{ id, name, team, charges, chargesAt, pixelsTotal }` |
| `config` | размер поля, команды, `maxCharges`, `regenMs` — присылает сервер |
| `round` | `{ id, startedAt, endsAt }` |
| `seq` | **до какого изменения клиент знает поле** |
| `board` | такие же типизированные массивы, как на сервере |
| `pending` | **очередь ходов**, ещё не подтверждённых сервером: `[{ actionId, x, y, baseVersion, roundId }]` |
| `clockOffset` | разница между часами сервера и браузера |

**`localStorage`**, ключ `pixel-battle:v1` (суффикс `v1` нужен на случай смены формата: тогда
просто меняется ключ):

```json
{
  "token": "Qk9vX2…43 символа",
  "player": { "id": "98a3…", "name": "Кира", "team": 2, "charges": 8, "chargesAt": 1760529606000, "pixelsTotal": 32 },
  "config": { "width": 64, "height": 40, "teams": [ … ], "maxCharges": 10, "regenMs": 3000 },
  "round": { "id": 7, "startedAt": 1760529000000, "endsAt": 1760529600000 },
  "seq": 121,
  "clockOffset": -42,
  "cells": [[3, 3, 0, 1], [10, 5, 0, 2], [11, 5, 2, 1]],
  "pending": [{ "actionId": "e8b5…", "x": 12, "y": 5, "baseVersion": 0, "roundId": 7 }]
}
```

* `cells` — только **непустые** клетки в виде `[x, y, команда, версия]`.
* **Когда сохраняется:** через 300 мс после изменения (несколько изменений подряд дают одну
  запись), а также сразу при `pagehide` (закрытие вкладки) и при уходе со вкладки
  (`visibilitychange` → `hidden`).
* **Что не сохраняется:** курсоры, счёт, онлайн, история. Сервер присылает их при каждом подключении.
* **Токен в `localStorage` — это и есть «аккаунт».** Если очистить данные сайта, появится новый
  игрок. В приватном окне свой `localStorage`, поэтому там будет другой игрок. Это удобно для
  демонстрации: обычное окно + приватное = два игрока.
* Посмотреть сохранённое: DevTools → Application → Local Storage → `http://localhost:8092`.
* Если `localStorage` недоступен (некоторые приватные режимы, переполнение), ошибка
  перехватывается и игра продолжает работать, только без сохранения.

### 4.4. Время

* В БД время хранится как `TIMESTAMPTZ`, в сообщениях — как миллисекунды Unix-времени.
* Часы браузера могут отставать от серверных на секунды и даже минуты. Поэтому сервер присылает в
  `welcome` поле `serverTime`, а клиент запоминает `clockOffset = serverTime − Date.now()`. Таймер
  раунда и восстановление зарядов клиент считает по **серверному** времени: `Date.now() + clockOffset`.
* Решения, где важен порядок (какой ход первый), принимает только сервер, и времени клиентов
  он не доверяет.

## 5. Связь: WebSocket и протокол

### 5.1. Почему WebSocket

HTTP устроен как «запрос → ответ»: сервер не может сам написать клиенту. Способы доставить
событие:

| Способ                       | Как работает                                            | Минусы                                       |
| ---------------------------- | ------------------------------------------------------- | -------------------------------------------- |
| **Polling**                  | клиент раз в секунду спрашивает «что нового?»           | задержка до интервала, много пустых запросов |
| **Long polling**             | сервер держит запрос открытым, пока не появится событие | новый запрос на каждое событие               |
| **SSE** (Server-Sent Events) | одно HTTP-соединение, сервер пишет поток событий        | только в одну сторону, сервер → клиент       |
| **WebSocket** ✔              | одно постоянное **двустороннее** соединение             | за обрывами нужно следить самим              |

Игре нужны обе стороны с минимальной задержкой: от клиента идут ходы и курсоры, от сервера —
рассылки. Поэтому выбран WebSocket. SignalR тоже предпочитает WebSocket из этих транспортов.

### 5.2. Как открывается соединение

1. Клиент строит адрес из адреса страницы: `ws://localhost:8092/ws`, а на HTTPS-хостинге —
   `wss://…/ws`, то есть с шифрованием.
2. Браузер отправляет **обычный HTTP-запрос** с заголовками `Upgrade: websocket`,
   `Connection: Upgrade` и `Sec-WebSocket-Key`.
3. Node.js вызывает у HTTP-сервера событие `upgrade`. `Hub` проверяет путь: если это не `/ws`,
   отвечает `404` и закрывает сокет. На `/ws` он передаёт запрос библиотеке `ws`
   (`noServer: true` + `handleUpgrade`).
4. Сервер отвечает `101 Switching Protocols` и `Sec-WebSocket-Accept = base64(SHA1(key + GUID))`.
   С этого момента TCP-соединение уже не HTTP, а поток **фреймов**: текстовых (у нас JSON),
   бинарных и управляющих (`ping`, `pong`, `close`).
5. Закрытие — фрейм `close` с кодом: `1000` — норма, `1001` — «ухожу» (сервер останавливается),
   `1008` — нарушение правил (флуд).

### 5.3. Все сообщения протокола

Формат — JSON-объект с полем `type`. Клиент → сервер (→) и сервер → клиент (←):

**`hello` →** первое сообщение после каждого (пере)подключения:

```json
{ "type": "hello", "token": null, "roundId": null, "lastSeq": null }      // первый визит
{ "type": "hello", "token": "Qk9vX2…", "roundId": 7, "lastSeq": 118 }     // вернулся, знает поле до №118
```

**`welcome` ←** ответ на `hello`, вся информация для старта:

```json
{
  "type": "welcome",
  "serverTime": 1760529606000,
  "config": { "width": 64, "height": 40, "teams": [{ "id": 0, "name": "Красные", "color": "#e5484d" }, …],
              "maxCharges": 10, "regenMs": 3000 },
  "round":  { "id": 7, "startedAt": 1760529000000, "endsAt": 1760529600000 },
  "player": { "id": "98a3…", "name": "Кира", "team": 2, "charges": 8, "chargesAt": 1760529606000, "pixelsTotal": 32 },
  "tokenRejected": false,
  "sync":   { "mode": "delta", "seq": 121, "changes": [[119, 10, 5, 0, 2], [121, 11, 5, 2, 1]] },
  "scores": { "teams": [{ "id": 0, "cells": 2 }, …], "players": [{ "id": "…", "name": "Алиса", "pixels": 2 }], "totalCells": 2560 },
  "history": [{ "id": 6, "winnerTeam": 1, "finishedAt": 1760529000000, "scores": { … },
               "board": { "width": 64, "height": 40, "cells": "..0011…" } }],
  "online": { "players": [{ "id": "98a3…", "name": "Кира", "team": 2 }], "spectators": 1 }
}
```

`sync` бывает двух видов:

* **снимок**: `{ "mode": "snapshot", "seq": 121, "cells": [[x, y, команда, версия], …] }` — все непустые клетки;
* **дельта**: `{ "mode": "delta", "seq": 121, "changes": [[seq, x, y, команда, версия], …] }` —
  только пропущенное. В примере изменения №119 и №121; №120 был конфликтом и в дельту не попал.

**`join` → / `joined` ←** — первый вход:

```json
{ "type": "join", "name": "Кира", "team": 2 }
{ "type": "joined", "token": "Qk9vX2…", "player": { "id": "98a3…", "name": "Кира", "team": 2, "charges": 10, … } }
```

**`paint` →** — ход:

```json
{ "type": "paint", "actionId": "e8b5…-…", "x": 11, "y": 5, "baseVersion": 0, "roundId": 7 }
```

`actionId` — UUID, который придумывает клиент. `baseVersion` — версия клетки, которую видел игрок.

**`paintResult` ←** — ответ автору хода:

```json
{ "type": "paintResult", "actionId": "e8b5…", "status": "ok",
  "cell": { "x": 11, "y": 5, "team": 2, "version": 1, "playerId": "98a3…", "playerName": "Кира" },
  "player": { …заряды после хода… } }

{ "type": "paintResult", "actionId": "71d0…", "status": "conflict",
  "cell": { "x": 10, "y": 5, "team": 0, "version": 2, "playerName": "Алиса", … }, "player": { … } }
```

Возможные `status`: `ok`, `conflict`, `no_charges`, `rejected` (с `reason: "round_over"`), `error`.
Повтор уже обработанного хода приходит с `duplicate: true`.

**`pixel` ←** — рассылка **всем** (включая автора), когда клетка перекрашена:

```json
{ "type": "pixel", "seq": 121, "x": 11, "y": 5, "team": 2, "version": 1, "playerId": "98a3…", "playerName": "Кира" }
```

**Остальные:**

| Сообщение | Пример | Назначение |
|---|---|---|
| `cursor` → | `{ "type": "cursor", "x": 10.4, "y": 5.7 }` или `{ x: null, y: null }` | где мышь (в долях клетки); `null` — мышь ушла с поля |
| `cursor` ← | `{ "type": "cursor", "id": "…", "name": "Кира", "team": 2, "x": 10.4, "y": 5.7 }` | курсор другого игрока (автору не отправляется) |
| `cursorGone` ← | `{ "type": "cursorGone", "id": "…" }` | игрок отключился, его курсор нужно убрать |
| `presence` ← | `{ "type": "presence", "online": { "players": [...], "spectators": 1 } }` | кто онлайн |
| `scores` ← | `{ "type": "scores", "scores": { … } }` | счёт команд и лучшие игроки раунда |
| `roundEnd` ← | `{ "type": "roundEnd", "roundId": 7, "winnerTeam": 1, "finishedAt": …, "scores": { … }, "board": { … } }` | раунд окончен: победитель, итоговый счёт и итоговая карта |
| `roundStart` ← | `{ "type": "roundStart", "round": { … }, "sync": { "mode": "snapshot", "cells": [] }, "scores": { … } }` | новый раунд, поле пустое |
| `ping` → / `pong` ← | `{ "type": "ping", "t": 1760529606000 }` → `{ "type": "pong", "t": …, "serverTime": … }` | проверка связи и замер задержки |
| `error` ← | `{ "type": "error", "code": "not_joined", "message": "Чтобы рисовать, войдите в игру" }` | ошибка; **соединение при этом не рвётся** |

### 5.4. Как сервер обрабатывает входящее сообщение

```
ws 'message'
  ├─ бинарный фрейм?            → error bad_message
  ├─ takeToken(): лимит частоты → превышен: сообщение отброшено, error rate_limited
  └─ client.chain = client.chain.then(() => handle(...))   ← сообщения клиента строго по порядку
        handle():
          parseClientMessage(raw)          → ProtocolError → error { code }, соединение живо
          switch (type):
            hello  → onHello   (синхронизация, welcome)
            join   → onJoin    (создать игрока, joined)
            paint  → onPaint   (game.paint → paintResult)
            cursor → onCursor  (разослать остальным)
            ping   → pong
        любая другая ошибка → error internal_error
```

**Зачем цепочка `chain` на каждого клиента?** Обработчики асинхронные. Без цепочки `paint`,
пришедший сразу за `hello`, мог бы начать выполняться раньше, чем закончится `hello`.
Цепочка гарантирует, что сообщения одного клиента обрабатываются в том порядке, в котором пришли.

### 5.5. Проверка входящих сообщений (`protocol.js`)

Всё, что прислал клиент, — **недоверенные данные**:

| Правило | Пример нарушения |
|---|---|
| корректный JSON-объект | `{not json` → `bad_json` |
| известный `type` | `{"type":"hack"}` → `unknown_type` |
| **никаких лишних полей** | `paint` с полем `team` → `bad_message` («Лишние поля: team») |
| координаты — целые числа в пределах поля | `x: 100` → `bad_message` |
| `actionId` — UUID | `"actionId": "1"` → `bad_message` |
| имя: 2–20 символов, пробелы схлопываются, управляющие символы запрещены | `"name": "a"` → `bad_message` |
| команда 0–3 | `team: 7` → `bad_message` |
| токен: 20–100 символов `[A-Za-z0-9_-]` | — |

Ошибки состояния проверяет `Hub`: `not_greeted` — `join` до `hello`; `already_greeted` —
второй `hello`; `not_joined` — `paint` от зрителя; `already_joined` — второй `join`.

### 5.6. Рассылка и прореживание

* `broadcast(message, except, { droppable })` отправляет сообщение всем клиентам с `ready = true`,
  кроме `except`. Сообщение сериализуется в JSON один раз, а не для каждого клиента.
* `ready` становится `true` только после отправки `welcome`. До этого клиент не получает
  рассылок: он ещё не знает поля, и применять к нему изменения рано.
* **Прореживание (throttle)**: часто меняющиеся данные рассылаются не на каждое изменение.

| Что        | Как часто                                                                | Почему                                                      |
| ---------- | ------------------------------------------------------------------------ | ----------------------------------------------------------- |
| `pixel`    | на каждый ход                                                            | основное событие, терять нельзя                             |
| `scores`   | не чаще раза в 500 мс                                                    | при 100 ходах в секунду не нужно 100 раз пересылать таблицу |
| `presence` | не чаще раза в 200 мс                                                    | несколько подключений подряд дают одну рассылку             |
| `cursor`   | клиент шлёт не чаще раза в 80 мс, сервер пропускает не чаще раза в 50 мс | курсор — самое частое и наименее важное                     |

* **Backpressure**: если у клиента скопилось больше 1 МБ неотправленных данных (медленная сеть),
  курсоры (`droppable`) ему больше не отправляются. Иначе медленный клиент раздувал бы память
  сервера. Важные сообщения (`pixel`) отправляются всегда.

## 6. Жизненный цикл клиента

### 6.1. Первый визит

```
Браузер                                              Сервер
  │ GET /  → index.html, styles.css, js/*.js         │
  │ state.load() — в localStorage пусто              │
  │ new WebSocket(ws://…/ws) ────────────────────────► upgrade → Hub.onConnection
  │ ── hello { token: null, roundId: null } ─────────►
  │                                                  │ игрок не найден; sync = снимок (в очереди)
  │ ◄──────── welcome { player: null, sync: snapshot, … }  client.ready = true
  │ рисует поле, открывает диалог «Имя + команда»    │
  │ ── join { name: "Кира", team: 2 } ───────────────►
  │                                                  │ INSERT INTO players (token_hash = sha256(token))
  │ ◄──────── joined { token, player }               │
  │ сохраняет token в localStorage                   │ presence → всем: «Кира онлайн»
```

### 6.2. Повторный визит (или перезагрузка вкладки)

```
  │ state.load() — есть сохранённое: поле, seq=118, token, очередь
  │ рисует сохранённую копию сразу (до ответа сервера)
  │ ── hello { token, roundId: 7, lastSeq: 118 } ────►
  │                                                  │ игрок найден по sha256(token)
  │                                                  │ раунд тот же, отстал на 2 изменения → дельта

  │ применяет дельту, досылает очередь pending       │
```

### 6.3. Что ещё делает `main.js`

* 4 раза в секунду обновляет таймер раунда, шкалу зарядов и строку статуса.
* Слушает `status` от `Connection`: на `open` отправляет `hello`, на остальных статусах
  ставит `ready = false`, и тогда ходы только копятся в очереди.
* Раздаёт сообщения сервера по обработчикам (`switch (message.type)`).

## 7. Путь одного хода

### 7.1. На клиенте (`main.js → paint(x, y)`)

1. Проверки до отправки: игрок вошёл? нет ли уже хода в эту клетку в очереди? клетка не своего
   цвета? есть ли заряд (по формуле на клиенте)? Если что-то не так, ход не отправляется, а
   игрок видит подсказку.
2. Формируется ход: `{ actionId: uuid(), x, y, baseVersion: версия клетки на экране, roundId }`.
3. Ход кладётся в `pending` и сохраняется в `localStorage`, заряд списывается локально.
4. Поле перерисовывается: клетка полупрозрачная, с пунктирной рамкой.
5. Если связь есть, ход отправляется. Если нет, он остаётся в очереди до переподключения.

### 7.2. На сервере (`Hub.onPaint → Game.paint → applyPaint`)

`game.paint()` ставит ход в `SerialQueue`, поэтому ходы обрабатываются строго по одному. Внутри:

```
1. findMove(player, actionId)    такой ход уже был?        → вернуть прежний результат, duplicate: true
2. roundId !== текущий раунд?                               → rejected, reason: round_over
3. BEGIN
     SELECT … FROM players WHERE id = $1 FOR UPDATE         строка игрока заблокирована до COMMIT
     заряды = currentCharges(игрок, сейчас)
     baseVersion ≠ версии клетки в памяти?                  → status = conflict
     иначе зарядов < 1?                                     → status = no_charges
     иначе writeCell (условная запись, раздел 8.4):
           не записалось?                                   → status = conflict
           записалось                                       → status = ok, заряд списан
     UPDATE players SET charges, charges_at, pixels_total
     INSERT INTO moves (…, status, cell_version) RETURNING seq
   COMMIT
4. если ok: обновить поле в памяти, seq, счёт
            emit('pixel')  → Hub рассылает pixel всем
            запланировать рассылку scores (через ≤ 500 мс)
5. вернуть { actionId, status, cell: актуальная клетка, player: заряды }
```

`Hub` отправляет автору `paintResult`. Если что-то упало (например, недоступна БД), транзакция
откатывается, а автор получает `paintResult { status: 'error' }`.

### 7.3. Порядок сообщений

`emit('pixel')` срабатывает внутри `applyPaint`, раньше, чем `paint()` вернёт результат.
Поэтому автор хода сначала получает `pixel` (как все), а потом `paintResult`. Клиенту порядок не
важен благодаря правилу из 7.4.

### 7.4. На клиенте после ответа

* `pixel`: `state.applyPixel()` применяет клетку, а если её закрасил другой игрок, клетка вспыхивает белым.
* `paintResult`: ход убирается из `pending`, заряды берутся из ответа сервера (они точнее
  локальных), а клетка приводится к `result.cell`.
* **Правило «побеждает бо́льшая версия»** (`setCell`): клетка обновляется, только если пришедшая
  версия не меньше известной. Версия в раунде только растёт, поэтому неважно, что придёт раньше
  — `pixel`, `paintResult` или дельта. Старое не перезапишет новое, а повтор ничего не испортит.

### 7.5. Все исходы хода

| Исход | Когда | Что в БД | Что видит игрок |
|---|---|---|---|
| `ok` | версия совпала, заряд есть | новая версия клетки, заряд списан, строка в `moves` | пунктир превращается в обычную клетку; у остальных клетка вспыхивает |
| `conflict` | клетку изменили после того, как игрок её увидел | строка в `moves` со статусом `conflict`, клетка и заряд не меняются | красный крестик и сообщение «клетку только что перекрасил игрок Алиса»; заряд возвращается |
| `no_charges` | локальная проверка пропустила, а сервер насчитал 0 | строка в `moves`, ничего не меняется | «Сервер отклонил ход: нет зарядов» |
| `rejected` | ход относится к уже закончившемуся раунду | ничего не пишется | ход тихо убирается из очереди |
| `duplicate` | этот `actionId` уже обрабатывали | ничего не меняется | тот же результат, что и в первый раз |
| `error` | сбой на сервере (БД недоступна) | транзакция откатилась | ход остаётся в очереди, повтор через 2 с |

## 8. Доп. требование 1 — конкурентный доступ и разрешение конфликтов

### 8.1. В чём проблема

Алиса и Боб одновременно видят пустую клетку и оба по ней кликают. Без защиты получается
**lost update** («потерянное обновление»): применится ход, обработанный вторым, а первый молча
пропадёт. Алиса будет уверена, что клетка её.

### 8.2. Подходы

| Подход | Суть | Почему не он (или он) |
|---|---|---|
| **Пессимистическая блокировка** | «захватить» клетку перед изменением, остальные ждут | лишний обмен сообщениями; при обрыве связи блокировка «зависает» |
| **Last-write-wins** | побеждает последний | изменения теряются, о конфликте никто не узнаёт |
| **Оптимистическая блокировка** ✔ | изменение несёт версию, которую видел автор, и принимается, только если версия не изменилась | дёшево, без блокировок, конфликт явно обнаруживается |
| **CRDT / OT** | структуры данных, которые сливаются без конфликтов (как в Google Docs) | избыточно: клетка — атомарное значение, сливать нечего |

### 8.3. Как сделано у нас

* У каждой клетки есть **`version`**: 0 у пустой и +1 при каждой перекраске.
* Клиент кладёт в ход **`baseVersion`** — версию, которую видит игрок.
* Сервер обрабатывает ходы **строго по одному** и сравнивает. Если `baseVersion` равна
  текущей версии, ход применяется и версия растёт. Иначе ход отклоняется как **`conflict`**: заряд не
  списывается, а в ответе приходят актуальная клетка и **имя того, кто её перекрасил**.
* **Политика — first-write-wins**: выигрывает ход, который **сервер обработал первым**, а не тот,
  по которому раньше кликнули. Часам клиентов доверять нельзя.

```
Алиса и Боб видят клетку (7, 7) пустой, версия 0
Алиса: paint (7,7) baseVersion=0  ─┐
Боб:   paint (7,7) baseVersion=0  ─┤  SerialQueue: строго по одному
                                   ├─► Алиса: 0 = 0 → ok, версия 1, pixel всем
                                   └─► Боб:   1 ≠ 0 → conflict, получает клетку Алисы,
                                              заряд не списан, красный крестик и подсказка
```

**Перекрасить чужую клетку — не конфликт**, а нормальный ход игры: игрок видел её актуальную
версию. Конфликт возникает, только если клетка изменилась **между** моментом, когда игрок её
увидел, и моментом обработки хода. Это и есть «одновременное редактирование одного элемента».

### 8.4. Почему защита двойная

**Слой 1 — в процессе: `SerialQueue`.** Node.js однопоточный, но это защищает только синхронный
код. Обработка хода содержит `await` (запросы к БД), и пока один ход ждёт БД, мог бы начаться
второй и прочитать ту же старую версию. Очередь не даёт следующему ходу начаться, пока не
закончился предыдущий:

```js
run(task) {
  const result = this.tail.then(task);          // встать в хвост
  this.tail = result.catch(() => undefined);    // ошибка одной задачи не ломает очередь
  return result;
}
```

Заодно порядок номеров `seq` в журнале совпадает с порядком применения, а это важно для дельты.

**Слой 2 — в БД: условная запись (compare-and-set).**

```sql
-- клетка уже была закрашена (baseVersion > 0)
UPDATE cells SET team = $4, player_id = $5, version = version + 1, updated_at = now()
 WHERE round_id = $1 AND x = $2 AND y = $3 AND version = $6     -- $6 = baseVersion
RETURNING version;          -- пустой ответ = версия уже другая = конфликт

-- клетка пустая (baseVersion = 0)
INSERT INTO cells (round_id, x, y, team, player_id, version) VALUES ($1, $2, $3, $4, $5, 1)
ON CONFLICT (round_id, x, y) DO NOTHING
RETURNING version;          -- пустой ответ = кто-то успел закрасить первым
```

Даже если копия в памяти разошлась с БД или работают два экземпляра сервера, двойной записи
не будет.

**Заряды** защищены `SELECT … FOR UPDATE`: строка игрока заблокирована до конца транзакции, поэтому
два хода одного игрока (например, из двух вкладок) не спишут заряд дважды с одного значения.

Аналог в .NET — `[ConcurrencyCheck]` / `rowversion` в Entity Framework и
`DbUpdateConcurrencyException`.

### 8.5. Как это проверить руками

1. Два окна, два игрока. В первом: DevTools → Network → **Offline**.
2. В первом окне закрасить клетку X: она рисуется пунктиром и ждёт в очереди.
3. Во втором окне закрасить ту же клетку X: ход сразу применяется, версия клетки растёт.
4. В первом вернуть сеть. Ход уходит с устаревшей `baseVersion` и получает `conflict`: на
   клетке красный крестик, сообщение «отклонено из-за конфликтов 1».
5. В журнале: `docker compose logs app | grep paint.conflict`.

## 9. Доп. требование 2 — обрыв связи и восстановление

### 9.1. Как замечается обрыв

| Ситуация | Кто замечает и как | Как быстро |
|---|---|---|
| сервер останавливается корректно | клиент получает `close` с кодом 1001 | сразу |
| процесс сервера убит или упал | клиент получает `close` (TCP-соединение разорвано) | сразу |
| у клиента пропал интернет | браузер генерирует `offline` → `connection.drop()` | сразу |
| «тихий» обрыв: уснул ноутбук, завис Wi-Fi, умер прокси | клиент: 12 с без единого сообщения от сервера; сервер: клиент не ответил `pong` | клиент — до 12 с, сервер — 15–30 с |

Почему нужны свои проверки: при «тихом» обрыве TCP может минутами считать соединение живым
(**полуоткрытое соединение**). Поэтому проверка идёт с обеих сторон:

* **Сервер** раз в 15 с отправляет протокольный фрейм `ping`. Клиент, не ответивший `pong` до
  следующей проверки, отключается (`terminate`) и пропадает из списка онлайн.
* **Клиент** протокольных ping/pong не видит (браузерный API их скрывает), поэтому раз в 5 с шлёт
  прикладной `{ type: 'ping' }`. Если 12 с не пришло ни одного сообщения, соединение
  считается мёртвым.

`drop()` не ждёт события `close`: без сети закрывающее рукопожатие может тянуться десятки секунд.
Соединение сразу считается потерянным, и планируется переподключение.

### 9.2. Переподключение

Задержка растёт **экспоненциально со случайным разбросом (jitter)**:

```
задержка = min(10 с, 0,5 с · 2^попытка) × случайное(0,5 … 1)
```

| Попытка | Задержка |
|---|---|
| 1 | 0,25–0,5 с |
| 2 | 0,5–1 с |
| 3 | 1–2 с |
| 4 | 2–4 с |
| 5 | 4–8 с |
| 6 и далее | 5–10 с |

* **Экспонента** не даёт заваливать лежащий сервер попытками.
* **Jitter** нужен, чтобы после перезапуска сервера сотни клиентов не постучались в одну
  миллисекунду (проблема **thundering herd**).
* Событие `online` и возвращение на вкладку (`visibilitychange`) сбрасывают счётчик и подключают
  сразу, без ожидания.
* В верхней панели статус: «В сети · 12 мс», «Подключение…» или «Нет связи · повтор через 3 с».

### 9.3. Игра без сети

* Рисовать можно: ходы рисуются пунктиром и копятся в `pending`. Баннер сообщает: «Ходов в
  очереди: N — они сохранены и будут отправлены после переподключения».
* Заряды тратятся и восстанавливаются локально по той же формуле, что на сервере.
* Очередь и поле лежат в `localStorage`, поэтому даже **перезагрузка вкладки без интернета**
  покажет поле и очередь («Показана сохранённая копия поля»).

### 9.4. Синхронизация после переподключения: дельта или снимок

Клиент отправляет `hello { token, roundId, lastSeq }`, и сервер (`Game.syncFor`) решает, что прислать:

| Ситуация | Ответ | Как получается |
|---|---|---|
| первый визит (`roundId = null`) | **снимок** | все непустые клетки из памяти |
| другой раунд (пока клиент был офлайн, раунд сменился) | **снимок** | старые клетки к новому полю не относятся |
| `lastSeq` больше, чем `seq` сервера (например, БД очистили) | **снимок** | клиент знает то, чего нет |
| тот же раунд, `lastSeq` = текущему | **пустая дельта** | ничего не пропущено |
| тот же раунд, отстал не больше чем на 2000 изменений | **дельта** | `SELECT … FROM moves WHERE round_id = $1 AND status = 'ok' AND seq > $lastSeq ORDER BY seq` |
| отстал больше чем на 2000 | **снимок** | на поле всего 2560 клеток, поэтому снимок уже не больше дельты |

Это **дельта-синхронизация по журналу событий**. По тому же принципу работают репликация БД по
WAL и Event Sourcing.

**Почему между снимком и следующим `pixel` ничего не теряется.** Расчёт `sync` и отправка
`welcome` выполняются **внутри очереди ходов** (`game.consistent(...)`), и там же клиенту ставится
`ready = true`. Пока считается синхронизация, ни один ход не может примениться. Все ходы,
обработанные после этого, разошлются уже и этому клиенту. Поэтому изменение не может ни
«проскочить» между снимком и рассылкой, ни прийти дважды.

### 9.5. Досылка очереди без дублей (идемпотентность)

После `welcome` клиент отправляет все ходы из `pending` заново. Опасный случай: связь оборвалась
**после** того, как сервер применил ход, но **до** того, как клиент получил ответ. Ход
остался в очереди и уйдёт повторно.

Решение — **`actionId`**:

* клиент генерирует UUID для каждого хода один раз, и при повторной отправке он не меняется;
* перед обработкой сервер ищет `(player_id, action_id)` в `moves`. Если ход найден, сервер
  возвращает прежний статус с `duplicate: true` и **ничего не меняет**;
* `UNIQUE (player_id, action_id)` в БД — страховка на уровне данных.

Это стандартный приём надёжной доставки: доставка **«как минимум один раз»** плюс
**идемпотентный обработчик** дают эффективно **«ровно один раз»**. Так же устроен заголовок
`Idempotency-Key` в платёжных API.

Ходы из очереди проверяются по **тем версиям клеток, которые игрок видел офлайн**. Если клетку
за это время кто-то перекрасил, ход получает `conflict`. Когда придут ответы на все ходы очереди,
игрок увидит итог:

> Офлайн-ходы отправлены: применено 3, отклонено из-за конфликтов 1 (эти клетки изменились, пока вас не было).

### 9.6. Особые случаи

| Случай | Что происходит |
|---|---|
| пока игрок был офлайн, **раунд сменился** | клиент сбрасывает очередь с предупреждением «раунд сменился — N неотправленных ходов отменено». Если бы ход всё-таки ушёл, сервер ответил бы `rejected` |
| сервер **не узнал токен** (например, БД удалили через `docker compose down -v`) | `welcome.tokenRejected = true`: клиент забывает игрока и открывает диалог входа |
| сервер ответил `error` (БД недоступна) | ход остаётся в очереди и повторяется через 2 с; `actionId` не даст применить его дважды |
| **перезапуск сервера** во время игры | клиенты получают 1001 и переподключаются; `seq` и поле восстановлены из БД, так что приходит дельта |
| **две вкладки одного игрока** | обе вкладки — один игрок (один токен). Заряды общие и защищены `FOR UPDATE`, а в списке онлайн игрок показан один раз |

### 9.7. Пример целиком

```
12:00:00  Кира знает поле до seq=121 (клетка (10,5) у неё версии 2), пропадает Wi-Fi
12:00:00  браузер: 'offline' → drop() → статус «Нет связи», баннер
12:00:02  Кира закрашивает (12,5) и (10,5)   → pending: 2 хода (baseVersion 0 и 2), сохранены в localStorage
12:00:03  Алиса (онлайн) перекрашивает (10,5) → на сервере версия (10,5) стала 3, seq=122
12:00:05  Кира перезагружает вкладку → поле и очередь из localStorage на месте
12:00:09  Wi-Fi вернулся → 'online' → connect()
          → hello { token, roundId: 7, lastSeq: 121 }
          ← welcome { sync: delta [122] }  — Кира видит ход Алисы
          → paint (12,5) baseVersion=0   ← paintResult ok
          → paint (10,5) baseVersion=2   ← paintResult conflict (версия уже 3), красный крестик
          «Офлайн-ходы отправлены: применено 1, отклонено из-за конфликтов 1»
```

## 10. Игровая логика: заряды и раунды

### 10.1. Заряды — «ленивое» восстановление

Держать таймер на каждого игрока не нужно. Хранится пара `(charges, charges_at)`: «столько
зарядов было в момент `charges_at`». Текущее значение досчитывается при обращении
(`game/charges.js`):

```
если charges ≥ max:  заряды = max, отсчёт = сейчас
иначе:
  gained  = floor((сейчас − charges_at) / regenMs)    сколько полных интервалов прошло
  заряды  = min(max, charges + gained)
  отсчёт  = charges_at + gained · regenMs              остаток неполного интервала не теряется
```

Пример (`max = 10`, `regenMs = 3 с`):

| Время      | Событие                                         | `charges` | `charges_at`                         |
| ---------- | ----------------------------------------------- | --------- | ------------------------------------ |
| 12:00:00.0 | было 10, закрасила 3 клетки                     | 7         | 12:00:00.0                           |
| 12:00:07.5 | спросили: прошло 7,5 с → 2 полных интервала     | 9         | 12:00:06.0 (1,5 с остатка сохранены) |
| 12:00:09.0 | прошло ещё 3 с от 12:00:06 → +1 = 10 = максимум | 10        | «сейчас»                             |

Плюсы: серверу не нужны таймеры, после перезапуска заряды считаются правильно, а функции
чистые (время передаётся параметром), что удобно тестировать.

Та же формула есть на клиенте (`util.js`). Шкала зарядов («+1 через 2 с») двигается плавно без
запросов к серверу, а время берётся серверное (`clockOffset`). **Решает всё равно сервер**: при
расхождении придёт `no_charges`, а `paintResult` всегда приносит точные заряды.

### 10.2. Раунды

* **Таймер**: `scheduleRoundEnd()` ставит `setTimeout` на `ends_at`. Когда он срабатывает,
  `rotateRound()` ставится **в ту же очередь, что и ходы**, поэтому конец раунда не может
  «разрезать» ход пополам.
* **`rotateRound()`**:
  1. Победитель — команда с наибольшим числом клеток. Если у двух команд поровну или поле пустое,
     объявляется ничья (`winner_team = NULL`).
  2. Поле из памяти кодируется в итоговую карту (`encodeBoard`).
  3. Одна транзакция:
     * из журнала `moves` считается, сколько игроков каждой команды участвовало;
     * `finishRound` сохраняет итоги в `rounds.scores`, а карту — в `rounds.final_board`;
     * `createRound` создаёт новый раунд с `ends_at = now() + 10 минут`;
     * `pruneRounds(10)` удаляет старые раунды, а пустой (если в нём никто не играл) — сразу.
  4. Поле в памяти очищается, ставится новый таймер.
  5. Рассылаются `roundEnd` и `roundStart`. По `roundEnd` клиенты на 5 секунд показывают оверлей
     «Победили Синие!» с итоговой картой и добавляют карточку в историю. Если в раунде никто не
     играл, вместо оверлея появляется короткое уведомление. По `roundStart` поле становится
     пустым, номер раунда меняется, а очередь клиента очищается.
* **Если сервер был выключен**, когда раунд должен был закончиться, `game.init()` при старте видит,
  что `ends_at` в прошлом, и сразу подводит итоги.
* Ход, отправленный в старый раунд (например, из офлайн-очереди), получает `rejected / round_over`.

Длительность раунда задаётся в `.env` (`ROUND_DURATION_SEC`). Для демонстрации удобно поставить
60 секунд.

## 11. Отрисовка и интерфейс (клиент без фреймворков)

### 11.1. Canvas (`renderer.js`)

* Поле рисуется на одном `<canvas>`. Логический размер клетки 16 CSS-пикселей, холст 64·16 × 40·16.
* **Чёткость на Retina-экранах**: физический размер холста умножается на `devicePixelRatio`, а
  контекст масштабируется `setTransform(dpr, …)`.
* **Рисование по требованию**: `requestDraw()` запрашивает один кадр через `requestAnimationFrame`.
  Анимационный цикл крутится, только пока есть вспышки, а в покое браузер ничего не
  перерисовывает и не тратит процессор.
* **Слои кадра** по порядку: клетки → сетка → свои неподтверждённые ходы (полупрозрачные, пунктир)
  → вспышки (белая 0,45 с — чужой ход; красный крестик 1,1 с — конфликт) → рамка клетки под
  мышью → курсоры других игроков с подписями.
* **Клик → клетка**: CSS может растянуть холст, поэтому координаты считаются через реальный
  размер на экране (`getBoundingClientRect`).
* Курсор игрока, ушедшего без `cursorGone`, исчезает сам через 5 секунд.
* **Итоговые карты** (история, оверлей конца раунда) рисует функция `drawFinalBoard`. Холст
  размером 64×40 — **один пиксель на клетку**. До нужного размера его растягивает CSS с
  `image-rendering: pixelated`, поэтому клетки остаются чёткими квадратами, а не размытыми
  пятнами. Пустые клетки прозрачные, их цвет — фон холста из CSS, так что карта сама следует
  светлой или тёмной теме.

### 11.2. DOM (`ui.js`, `util.js`)

* Элементы создаются функцией `el(tag, { className, text, attrs }, children)`. Текст задаётся
  **только через `textContent`**, а `innerHTML` с данными игроков не используется нигде. Поэтому
  имя вроде `<img onerror=…>` отображается как текст и не выполняется (защита от XSS).
* Диалог входа — нативный `<dialog>` с `showModal()`. Есть кнопка «Просто посмотреть» для
  зрителей.
* Статус сети (точка + текст + задержка), баннер при обрыве, уведомления (toasts), оверлей
  конца раунда.
* **История раундов** — сетка карточек под полем. В каждой карточке: номер и время, итоговая
  карта, результат («Победили Синие» или «Ничья»), команды, которые играли (по убыванию
  территории: клетки к концу, доля поля, число игроков), и строка «Не участвовали: …». Полоса
  сверху карточки окрашена в цвет победителя.
* Раскладка — CSS Grid с именованными областями: на широком экране поле и под ним история слева,
  боковая панель справа; на узком всё в одну колонку (поле → панель → история).
* Темы: цвета заданы CSS-переменными, а `@media (prefers-color-scheme: dark)` подменяет их
  для тёмной темы. Renderer перечитывает цвета при смене темы.

### 11.3. Почему это «без фреймворков»

* **Клиент**: ни React/Vue, ни сборщика. Браузер грузит ES-модули напрямую:
  `<script type="module" src="js/main.js">` и `import … from './state.js'`.
* **Сервер**: ни Express, ни Socket.IO. HTTP — встроенный модуль `http`; маршрутизация, раздача
  статики, ETag и заголовки написаны руками.
* Две зависимости — **библиотеки, а не фреймворки**: `ws` реализует протокол WebSocket (разбор
  фреймов, маскирование, ping/pong), `pg` — драйвер PostgreSQL. Разница в том, кто кого вызывает:
  **фреймворк** задаёт архитектуру и сам вызывает твой код («Hollywood principle»), а
  **библиотеку** вызываешь ты. Socket.IO был бы уже фреймворком со своим протоколом поверх
  WebSocket.

## 12. HTTP-часть без Express

`http/app.js`, обработчик всех запросов:

| Запрос | Ответ |
|---|---|
| `GET /api/health` | `200 {"status":"ok","database":"up"}`; при недоступной БД `503` + `Retry-After: 5`. Используется healthcheck'ом Docker и Render |
| `GET /api/state` | раунд, счёт, онлайн, `seq` — для проверки и отладки |
| `GET /api/что-то-ещё` | `404` |
| любой метод, кроме `GET`/`HEAD` | `405` + заголовок `Allow: GET, HEAD` |
| остальное | файл из `public/` (`static.js`) |

**Заголовки безопасности** (на каждом ответе):

* `Content-Security-Policy`: `default-src 'self'; script-src 'self'; style-src 'self';
  connect-src 'self' ws: wss:; frame-ancestors 'none'; …`. Скрипты и стили грузятся только со
  своего сервера, встроенные `<script>` запрещены, WebSocket разрешён, встраивать страницу в
  чужой `<iframe>` нельзя (защита от clickjacking).
* `X-Content-Type-Options: nosniff`: браузер не угадывает тип файла.
* `Referrer-Policy: no-referrer`.

**Раздача файлов (`static.js`)**:

* **Path traversal**: путь декодируется, нормализуется (`/../../etc/passwd` → `/etc/passwd`)
  и разрешается **относительно** `public/`. Затем проверяется, что итоговый путь начинается с
  `public/`, иначе `403`.
* **ETag**: `W/"размер-время_изменения"`. Если браузер пришлёт `If-None-Match` с тем же
  значением, сервер ответит `304 Not Modified` без тела.
* `Cache-Control: no-cache` значит «кешировать можно, но перед использованием сверяться». Имена
  файлов без хешей, поэтому после обновления приложения браузер сразу получит новые версии.

## 13. Надёжность и безопасность — сводка

| Угроза или ситуация | Защита |
|---|---|
| клиент присылает мусор или подделку | строгая проверка каждого сообщения (`protocol.js`); команду и заряды знает только сервер |
| флуд сообщениями | token bucket: 25 сообщений в секунду, всплеск до 50; лишние отбрасываются, после 200 нарушений соединение закрывается с кодом 1008 |
| огромное сообщение | `maxPayload: 16 КБ` |
| медленный клиент раздувает память | backpressure: при > 1 МБ в буфере курсоры ему не шлются |
| XSS через имя игрока | только `textContent` и Canvas + строгий CSP |
| path traversal | нормализация и проверка префикса пути |
| кража базы | в БД только SHA-256 токенов |
| одновременные ходы | `SerialQueue` + compare-and-set в SQL + `FOR UPDATE` |
| повторная отправка хода | `actionId` + `UNIQUE (player_id, action_id)` |
| перезапуск сервера | всё в PostgreSQL; код 1001 и автоматическое переподключение; ходы из очереди дописываются перед остановкой |
| обрыв соединения | heartbeat с двух сторон, переподключение с экспоненциальной задержкой и jitter, `localStorage` |
| Postgres стартует позже приложения | `waitForDatabase` (30 попыток) + `depends_on: condition: service_healthy` |
| процесс в контейнере | запуск от пользователя `node`, не root |

## 15. Тесты и CI

`npm test` запускает 29 тестов на встроенном раннере `node:test`. Каждый интеграционный тест
поднимает **настоящий сервер** на случайном порту (`port: 0`) с **настоящим PostgreSQL**
(таблицы очищаются через `TRUNCATE` перед тестом) и подключает WebSocket-клиентов. Тесты идут
последовательно (`--test-concurrency=1`), потому что база общая.

* `unit.test.js` (9): формула зарядов (восстановление, остаток интервала, трата), протокол
  (корректный ход, клетки за полем, лишние поля, не-UUID, имя, курсор), `SerialQueue` (порядок,
  изоляция ошибок).
* `game.test.js` (20):
  * токен узнаётся при повторном входе; ход приходит всем, включая зрителей; список онлайн;
  * **два одновременных хода в одну клетку**: ровно один `ok`, второй `conflict` с актуальной
    клеткой и несписанным зарядом; в БД версия 1;
  * ход по устаревшей версии отклоняется, по актуальной проходит;
  * **повтор того же `actionId`** не применяет ход дважды (в `moves` одна строка);
  * без зарядов → `no_charges`;
  * **дельта после переподключения** содержит только пропущенное; другой раунд → снимок;
  * **офлайн-очередь**: свободная клетка → `ok`, занятая за время офлайна → `conflict`;
  * **перезапуск сервера**: поле, игрок, заряды и счёт на месте; раунд, истёкший при выключенном
    сервере, завершается при старте;
  * конец раунда: победитель, чистое поле, ходы старого раунда → `rejected`;
  * **история**: итоговая карта посимвольно совпадает с полем; команда, которая играла, но
    осталась без клеток, учтена как участник; то же самое сохранено в БД и приходит в `welcome`;
  * раунд, в котором никто не играл, в историю не попадает и удаляется;
  * очистка оставляет последние сыгранные раунды и удаляет пустые;
  * ошибки протокола не рвут соединение; флуд ограничивается;
  * HTTP: CSP, ETag/304, `/api/health`, 405, 404, WebSocket только на `/ws`.

**CI** (`.github/workflows/lab4.yml`) запускается на каждый push, затрагивающий `Lab4/`:
`npm ci` → ESLint → тесты (PostgreSQL поднимается как service-контейнер) → `npm audit` → проверка
`docker-compose.yml` и сборка образа.

## 16. Развёртывание

* **`Dockerfile`**: `node:22-alpine`. Сначала копируются `package*.json` и выполняется
  `npm ci --omit=dev`; этот слой кешируется и пересобирается только при смене зависимостей. Затем
  копируются `src` и `public`, процесс запускается от пользователя `node`, порт берётся из `PORT`.
* **`docker-compose.yml`**: `db` (данные в именованном томе `pgdata`, healthcheck через `pg_isready`)
  и `app` (стартует, когда `db` здоров; свой healthcheck по `/api/health`; `restart: unless-stopped`).
  * `docker compose down` — данные остаются;
  * `docker compose down -v` — том удаляется, вместе с ним все данные.
* **`render.yaml`** (Blueprint для Render, в корне репозитория): веб-сервис из `Lab4/Dockerfile`
  и бесплатная PostgreSQL, связанные через `DATABASE_URL`; health check `/api/health`.
  Render → **New → Blueprint** → выбрать репозиторий.
* На HTTPS-хостинге клиент сам выбирает `wss://` (`location.protocol === 'https:'`), так что
  WebSocket-трафик шифруется.
* Для облачных БД с TLS (Neon, Supabase) есть `DATABASE_SSL=true`.

## 17. Сценарий демонстрации

1. `cd Lab4 && docker compose up --build`. Открыть <http://localhost:8092> в **обычном и
   приватном окне** и войти разными игроками в разные команды.
2. **Синхронизация**: клик в одном окне, и клетка мгновенно появляется во втором с белой
   вспышкой. Видно курсор соседа с подписью, меняются счёт и список онлайн.
3. **Конфликт** (раздел 8.5): Offline в первом окне → закрасить X → закрасить X во втором →
   Online → красный крестик и «отклонено из-за конфликтов 1».
4. **Офлайн**: Offline → нарисовать несколько клеток (пунктир, «Ходов в очереди: N») →
   **перезагрузить вкладку** (всё на месте) → Online → «Офлайн-ходы отправлены: применено N».
5. **Перезапуск сервера**: `docker compose restart app` → в окнах «Нет связи · повтор через…»,
   через пару секунд снова «В сети», поле на месте.
6. **Сохранение**: `docker compose down && docker compose up -d` → игра продолжается с того же места.
7. **Данные**: `docker compose exec db psql -U pixels -d pixels -c "SELECT seq, x, y, status, cell_version FROM moves ORDER BY seq DESC LIMIT 5"`.
   В DevTools → Application → Local Storage виден `pixel-battle:v1`.
8. **Журнал**: `docker compose logs app | grep paint.conflict`.
9. **История**: в `.env` поставить `ROUND_DURATION_SEC=60`, сыграть раунд двумя игроками →
   оверлей с итоговой картой, а под полем — карточка раунда с картой и счётом команд. Данные:
   `SELECT id, winner_team, scores, left(final_board->>'cells', 64) FROM rounds;`.

## 18. Вопросы на защите

**Где хранится поле?** В PostgreSQL, в таблице `cells`: одна строка на закрашенную клетку,
ключ — `(round_id, x, y)`. Сервер держит копию текущего раунда в памяти для скорости, браузер —
свою копию в памяти и в `localStorage`.

**Что будет, если перезапустить сервер?** Клиенты получат код 1001 или заметят обрыв и
переподключатся с нарастающей задержкой. Сервер при старте загрузит поле из БД, а клиенты
получат дельту. Ничего не теряется.

**Что будет, если очистить `localStorage`?** Клиент получит снимок поля с сервера, но токен
пропадёт, поэтому придётся войти заново, уже новым игроком.

**Почему WebSocket, а не запросы раз в секунду?** Двусторонний канал без задержки и без лишних
запросов: сервер сообщает о событии в тот момент, когда оно произошло.

**Что такое «авторитетный сервер»?** Клиент присылает только намерение, а сервер решает, применить
ли его, и рассылает результат. Подменить состояние у себя и обмануть игру нельзя.

**Зачем очередь, если Node.js однопоточный?** Однопоточность защищает только синхронный код.
Обработка хода содержит `await`, и пока один ход ждёт БД, начал бы обрабатываться другой.

**Почему версия, а не время изменения?** Часы клиентов и даже серверов расходятся, а версия — точный
счётчик: «ты видел изменение №5, а сейчас уже №6».

**Зачем проверять версию дважды — в памяти и в SQL?** Проверка в памяти быстрая и даёт ответ без
лишней записи. Условный `UPDATE … WHERE version = $base` — гарантия на уровне данных на случай,
если копия в памяти и БД разойдутся или серверов станет несколько.

**Что увидит игрок при конфликте?** Его ход откатится, на клетке мигнёт красный крестик,
появится сообщение, кто её перекрасил, а заряд вернётся.

**Как гарантируется, что ход не применится дважды?** `actionId` (UUID от клиента) +
`UNIQUE (player_id, action_id)`. На повтор сервер возвращает прежний результат.

**Зачем писать в журнал отклонённые ходы?** Чтобы повтор того же `actionId` получил тот же вердикт,
а не был обработан заново.

**Как клиент узнаёт, что пропустил?** По `lastSeq` — номеру последнего известного изменения.
Сервер присылает из журнала `moves` все применённые изменения новее этого номера.

**Почему иногда приходит снимок, а не дельта?** Если раунд сменился или клиент отстал больше чем на
2000 изменений, всё поле (не больше 2560 клеток) отправить не дороже.

**Почему в `seq` бывают пропуски?** Номер берут и отклонённые ходы, и откатившиеся транзакции.
Для дельты важен только порядок, а не непрерывность.

**Как хранится итоговая карта раунда?** В `rounds.final_board`: строка по символу на клетку
(`'0'`–`'3'` — команда, `'.'` — пусто) плюс ширина и высота. Сохраняется в той же транзакции,
что и итоги раунда. Клиент рисует её на холсте с пикселем на клетку.

**Откуда известно, какие команды играли?** Из журнала `moves`: число разных игроков каждой команды
с хотя бы одним применённым ходом. По карте этого не понять: команду могли полностью перекрасить.

**Почему в истории нет некоторых номеров раундов?** Раунды без игроков удаляются сразу, чтобы
пустые раунды во время простоя не вытесняли из истории сыгранные.

**Как хранятся заряды, если нет таймеров?** Пара «сколько было» + «когда». Текущее значение
вычисляется формулой при обращении.

**Почему токен, а не пароль? Безопасно ли?** Регистрация не требуется. Токен — 256 случайных бит,
в БД хранится только его SHA-256, так что украденная база не позволит войти за игрока.

**Где здесь «без фреймворков», если есть npm-пакеты?** `ws` и `pg` — библиотеки: протокол
WebSocket и драйвер БД. Архитектура, маршрутизация, синхронизация и интерфейс написаны на чистом
JavaScript.

**Как масштабировать на несколько серверов?** Рассылку перевести на общий канал (Redis Pub/Sub или
PostgreSQL `LISTEN/NOTIFY`), а очередь в процессе заменить блокировками в БД. Условная запись уже
есть. Сейчас работает один процесс: для лабораторной этого достаточно, и так проще объяснить.

## 19. Словарь терминов

| Термин | Что значит у нас |
|---|---|
| **Авторитетный сервер** | состояние игры меняет только сервер; клиент присылает намерения |
| **Оптимистичный интерфейс** | ход показывается сразу, до ответа сервера, и откатывается при отказе |
| **Оптимистическая блокировка** | изменение несёт версию, которую видел автор, и принимается, только если версия не изменилась |
| **Compare-and-set (CAS)** | атомарная операция «записать, только если текущее значение равно ожидаемому»: `UPDATE … WHERE version = $base` |
| **First-write-wins** | при конфликте побеждает изменение, которое сервер обработал первым |
| **Lost update** | потерянное обновление: второе изменение молча затирает первое |
| **Идемпотентность** | повторное выполнение операции даёт тот же результат, что и однократное |
| **Снимок (snapshot)** | всё поле целиком |
| **Дельта (delta)** | только изменения после известного клиенту номера |
| **`seq`** | порядковый номер записи в журнале ходов |
| **Heartbeat** | периодический ping/pong, чтобы заметить «тихо» умершее соединение |
| **Полуоткрытое соединение** | одна сторона уже пропала, а другая всё ещё считает соединение живым |
| **Экспоненциальная задержка + jitter** | интервал между попытками удваивается и случайно варьируется |
| **Thundering herd** | все клиенты одновременно ломятся в только что поднявшийся сервер |
| **Throttle (прореживание)** | событие отправляется не чаще заданного интервала |
| **Backpressure** | не слать медленному получателю больше, чем он успевает принять |
| **Token bucket** | ограничение частоты: «ведро» жетонов пополняется с постоянной скоростью, каждое сообщение тратит жетон |
| **Типизированный массив** | `Int8Array`/`Int32Array` — компактный массив чисел фиксированного типа и размера |
| **Частичный индекс** | индекс только по строкам, удовлетворяющим условию `WHERE` |
| **Write-ahead** | сначала надёжно сохранить, потом объявить (сначала `COMMIT`, потом рассылка) |
