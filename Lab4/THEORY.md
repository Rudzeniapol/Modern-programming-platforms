# Теория к лабораторной работе №4
### Многопользовательская игра в реальном времени: WebSocket, конкурентный доступ, офлайн-режим

**Для человека, который знает C#/.NET.** Ближайший аналог всего, что здесь сделано руками, —
**ASP.NET Core SignalR**: хаб, рассылка всем клиентам, автоматическое переподключение. Только у нас
нет SignalR, а есть «голый» протокол WebSocket и свой протокол сообщений поверх него.

---

## 0. Что сделано (на одном дыхании)

«Пиксельная битва»: четыре команды закрашивают клетки общего поля 64×40. Каждый клик —
это сообщение по WebSocket. Сервер проверяет ход, записывает его в PostgreSQL и **мгновенно
рассылает всем**. У каждой клетки есть **версия**: если двое одновременно красят одну клетку,
применится первый ход, а второй получит **конфликт** и увидит, кто его опередил. При обрыве
связи клиент **сохраняет состояние и очередь ходов** в `localStorage`, сам переподключается,
получает **только пропущенные изменения** и досылает очередь **без дублей**. Данные живут в
PostgreSQL, поэтому игра переживает перезапуск сервера. Фреймворков нет ни на клиенте,
ни на сервере.

**Фраза для защиты:** «Сервер авторитетен: клиент шлёт намерения, сервер решает. Синхронизация —
WebSocket с рассылкой изменений. Конфликты решаются оптимистической блокировкой по версии клетки,
политика first-write-wins. Офлайн — локальное сохранение, очередь ходов с идемпотентными
`actionId` и дельта-синхронизация по порядковому номеру изменений».

## 2. Требование 1 — WebSocket и мгновенная синхронизация

### 2.1. Почему не HTTP

HTTP — это «запрос → ответ»: сервер не может сам написать клиенту. Варианты «доставить событие»:

| Способ | Как работает | Минусы |
|---|---|---|
| **Polling** | клиент каждую секунду спрашивает «что нового?» | задержка до интервала, куча пустых запросов |
| **Long polling** | сервер держит запрос открытым, пока не появится событие | новый запрос на каждое событие, накладные расходы |
| **SSE** (Server-Sent Events) | одно HTTP-соединение, сервер пишет поток событий | только сервер → клиент |
| **WebSocket** | одно постоянное **двустороннее** соединение | нужно самим следить за обрывами |

Для игры нужны обе стороны с минимальной задержкой (ходы и курсоры от клиента, рассылка от
сервера), поэтому выбран WebSocket. SignalR, кстати, сам выбирает из этих транспортов,
предпочитая WebSocket.

### 2.2. Как устроен WebSocket (RFC 6455)

1. **Handshake** — обычный HTTP-запрос с заголовками `Upgrade: websocket`,
   `Connection: Upgrade`, `Sec-WebSocket-Key`. Сервер отвечает `101 Switching Protocols` и
   `Sec-WebSocket-Accept = base64(SHA1(key + GUID))`. После этого TCP-соединение больше не
   HTTP, а поток **фреймов**.
2. **Фреймы**: текстовые (у нас JSON), бинарные, а также управляющие `ping`, `pong` и `close`.
   Фреймы от клиента к серверу маскируются (XOR с 4-байтовым ключом), чтобы защитить
   промежуточные прокси от отравления кеша.
3. **Закрытие** — фрейм `close` с кодом: `1000` — норма, `1001` — «ухожу» (мы шлём его при
   остановке сервера), `1008` — нарушение правил (флуд).

У нас HTTP и WebSocket работают **на одном порту**: `http.createServer` отдаёт статику, а событие
`upgrade` для пути `/ws` передаётся библиотеке `ws` (`noServer: true` + `handleUpgrade`).
Запрос на апгрейд по любому другому пути получает 404.

### 2.3. Что значит «только JavaScript, без фреймворков»

* **Клиент**: никакого React/Vue и никакого сборщика. Браузер грузит ES-модули напрямую
  (`<script type="module">`, `import … from './state.js'`). DOM строится через
  `document.createElement`, поле рисуется через Canvas 2D API.
* **Сервер**: никакого Express или Socket.IO. HTTP — встроенный модуль `http`; маршрутизация,
  раздача статики, ETag, заголовки безопасности написаны руками.
* Две зависимости — **библиотеки, а не фреймворки**: `ws` реализует протокол WebSocket (разбор
  фреймов, маскирование, ping/pong), `pg` — драйвер PostgreSQL. Разница: фреймворк задаёт
  архитектуру и вызывает твой код («Hollywood principle»), а библиотеку вызываешь ты сам.
  Socket.IO был бы уже фреймворком со своим протоколом поверх WebSocket.

### 2.4. Протокол сообщений

Свой протокол поверх WebSocket — JSON `{ type, ...поля }`. Полная таблица — в README. Главное:

* `hello` → `welcome` — синхронизация после (пере)подключения;
* `paint` → `paintResult` лично отправителю + `pixel` **всем**;
* `cursor` — эфемерные данные: не сохраняются, прореживаются (не чаще раза в 50–80 мс), медленным
  клиентам не отправляются;
* `scores`, `presence` — тоже прореживаются (throttle 500 и 200 мс): при 100 ходах в секунду не
  нужно 100 раз в секунду пересылать таблицу счёта.

### 2.5. Путь одного хода

```
клик ─► main.paint(): локальная проверка (заряды, не своя ли клетка)
      ─► ход сразу виден на поле пунктиром (оптимистичный UI), заряд списан локально
      ─► send { type:'paint', actionId, x, y, baseVersion, roundId }
сервер:
 hub ─► protocol.parseClientMessage   (некорректно → error, соединение живо)
     ─► game.paint ─► SerialQueue (строго по одному)
         ─► уже был такой actionId?            → вернуть прежний результат
         ─► roundId не текущий?                → rejected
         ─► BEGIN
              SELECT … FROM players FOR UPDATE   (заряды игрока)
              версия клетки ≠ baseVersion?       → conflict
              нет зарядов?                       → no_charges
              UPDATE cells … WHERE version = $base  (compare-and-set)
              UPDATE players (заряды, счётчик)
              INSERT INTO moves (…) RETURNING seq
            COMMIT
         ─► обновить поле в памяти, emit('pixel')
 hub ─► paintResult отправителю, pixel всем остальным
клиент: убрать ход из очереди; при conflict — красный крестик и подсказка «клетку перекрасил X»
```

**Сначала БД, потом память и рассылка.** Если запись в БД упала, никто не увидит изменения,
которого не существует. Это принцип write-ahead: сначала надёжно сохранить, потом объявить.

## 3. Требование 3 — сохранение между запусками

### 3.1. Схема БД

```
players  id, token_hash (SHA-256 токена), name, team, charges, charges_at, pixels_total, …
rounds   id, started_at, ends_at, finished_at, winner_team, scores (JSONB)
         уникальный индекс ((true)) WHERE finished_at IS NULL — активный раунд может быть только один
cells    (round_id, x, y) PK, team, player_id, version, updated_at
         нет строки = пустая клетка версии 0
moves    seq BIGSERIAL PK, round_id, player_id, action_id, x, y, team, status, cell_version
         UNIQUE (player_id, action_id) — идемпотентность
         частичный индекс (round_id, seq) WHERE status = 'ok' — быстрые дельты
```

* **Поле привязано к раунду** (`cells.round_id`): новый раунд — это просто новый `round_id`,
  а старые поля остаются в истории. Хранятся последние 10 раундов (`pruneRounds`).
* **`moves` — журнал событий**. Он одновременно даёт порядковый номер изменений для дельты,
  защиту от дублей и статистику игроков.

### 3.2. Что происходит при старте сервера (`Game.init`)

1. `migrate()` — идемпотентный `schema.sql` (`CREATE TABLE IF NOT EXISTS`).
2. Найти активный раунд или создать его.
3. Загрузить поле раунда из `cells` в память (`Int8Array` команд, `Int32Array` версий) и счётчики
   игроков из `moves`.
4. Если раунд **должен был закончиться, пока сервер был выключен**, сразу подвести итоги и
   начать новый.
5. Поставить таймер конца раунда.

Копия поля в памяти — это **кеш**, а источник истины — БД. Кеш нужен, чтобы мгновенно отдавать
снимок и счёт, а не делать `SELECT` на каждое подключение.

### 3.3. Игроки без пароля

Входа по паролю нет (не требуется). При первом `join` сервер генерирует случайный токен на 32
байта, возвращает его клиенту, а в БД хранит **только SHA-256** от токена. Клиент держит токен в
`localStorage` и при каждом подключении передаёт его в `hello`, так что после перезагрузки
страницы, обрыва или перезапуска сервера игрок остаётся тем же: с тем же именем, командой и
зарядами.

### 3.4. Заряды «лениво»

Таймер на каждого игрока не нужен. Хранится пара `(charges, charges_at)` — сколько зарядов было
в момент `charges_at`. Текущее значение досчитывается при обращении:

```
gained  = floor((now − charges_at) / regenMs)
charges = min(max, charges + gained)
charges_at += gained · regenMs   (остаток неполного интервала не теряется)
```

Поэтому заряды правильно восстанавливаются и после перезапуска сервера. Та же формула есть на
клиенте (`util.js`), чтобы шкала зарядов двигалась плавно без запросов к серверу. Разница часов
клиента и сервера учитывается через `serverTime` из `welcome` (`clockOffset`).

## 4. Доп. требование 1 — конкурентный доступ и разрешение конфликтов

### 4.1. В чём проблема

Алиса и Боб одновременно видят пустую клетку и оба по ней кликают. Без защиты получается
**lost update**: применится тот ход, что обработан вторым, а первый молча пропадёт. Алиса
будет думать, что клетка её.

### 4.2. Подходы

| Подход | Суть | Почему не он (или он) |
|---|---|---|
| **Пессимистическая блокировка** | «захватить» клетку перед изменением, остальные ждут | лишний обмен сообщениями, «зависшие» блокировки при обрыве связи |
| **Last-write-wins** | побеждает последний | теряются изменения, никто не узнаёт о конфликте |
| **Оптимистическая блокировка** ✔ | изменение несёт версию, которую видел автор; принимается, только если версия не изменилась | дёшево, без блокировок, конфликт явно обнаруживается |
| **CRDT / OT** | структуры данных, которые сливаются без конфликтов (как в Google Docs) | избыточно: клетка — атомарное значение, сливать нечего |

### 4.3. Как сделано у нас

* У каждой клетки есть **`version`**: 0 — пустая, и при каждой перекраске она растёт на 1.
* Клиент кладёт в ход **`baseVersion`** — версию клетки, которую видит игрок.
* Сервер обрабатывает ходы **строго по одному** (`SerialQueue`) и сравнивает:
  `baseVersion === текущая версия` → ход применяется, версия +1;
  иначе → **`conflict`**: ход отклонён, заряд **не списан**, в ответе — актуальное состояние
  клетки и **имя того, кто её перекрасил**.
* Клиент откатывает свой оптимистичный ход, рисует на клетке **красный крестик** и показывает
  «Конфликт: клетку (7,7) только что перекрасил игрок Алиса».

**Политика — first-write-wins**: «первым» считается тот ход, который первым обработал сервер,
а не тот, на который раньше кликнули: часам клиентов доверять нельзя. Если игрок хочет
перекрасить клетку, он видит её новое состояние и кликает снова, уже по актуальной версии.

### 4.4. Почему защита двойная

1. **В процессе** — `SerialQueue`. Node.js однопоточный, но обработка хода содержит `await`
   (запросы к БД), и между ними другой ход мог бы «вклиниться» и прочитать ту же старую версию.
   Очередь исключает это: следующий ход начинается только после завершения предыдущего.
   Заодно порядок номеров `seq` в журнале совпадает с порядком применения, что важно для дельты.
2. **В БД** — условная запись (**compare-and-set**):
   ```sql
   UPDATE cells SET team = …, version = version + 1
    WHERE round_id = $1 AND x = $2 AND y = $3 AND version = $base
   RETURNING version          -- нет строки в ответе = версия уже другая = конфликт
   ```
   Для пустой клетки — `INSERT … ON CONFLICT DO NOTHING`. Даже если бы работали два экземпляра
   сервера с одной БД, двойной записи не будет. Строка игрока блокируется `FOR UPDATE`, поэтому
   заряды не спишутся дважды.

Аналог в .NET — `[ConcurrencyCheck]` / `rowversion` в Entity Framework и
`DbUpdateConcurrencyException`.

### 4.5. Почему не last-write-wins для «перекраски чужой клетки»

Перекрасить чужую клетку — нормальный ход игры, и это **не** конфликт: игрок видел её актуальную
версию. Конфликт возникает, только если клетка изменилась **между** моментом, когда игрок её увидел,
и моментом обработки хода, то есть именно при «одновременном редактировании одного элемента».

## 5. Доп. требование 2 — потеря соединения и восстановление

### 5.1. Как заметить обрыв

* WebSocket сообщает `close`, но **не всегда вовремя**: если выдернуть кабель или ноутбук уснёт,
  TCP может считать соединение живым минутами («полуоткрытое соединение»).
* **Сервер** раз в 15 с шлёт протокольный `ping`. Клиент, не ответивший `pong` до следующей
  проверки, отключается (`terminate`) и убирается из списка онлайн.
* **Клиент** не видит протокольные ping/pong (браузерный API их скрывает), поэтому раз в 5 с шлёт
  прикладной `ping`. Если 12 с не пришло ни одного сообщения, соединение считается мёртвым.
* События браузера `offline`/`online` и возврат на вкладку (`visibilitychange`) реагируют
  мгновенно.

### 5.2. Переподключение

Задержка **растёт экспоненциально со случайным разбросом (jitter)**:
`min(10 с, 0,5 с · 2^попытка) × случайно(0,5…1)`. Экспонента не даёт заваливать сервер
попытками. Jitter нужен, чтобы после перезапуска сервера сотни клиентов не постучались в одну и
ту же миллисекунду («thundering herd»). Это то же, что `WithAutomaticReconnect` в SignalR.

### 5.3. Состояние не теряется

`GameState` сохраняет в `localStorage` токен, игрока, конфигурацию, раунд, **поле с версиями
клеток**, **`seq`** (до какого изменения клиент знает поле) и **очередь неподтверждённых ходов**.
Сохранение происходит с задержкой 300 мс после изменения, а также при `pagehide` и уходе со
вкладки.

Поэтому:
* без сети можно продолжать рисовать: ходы видны пунктиром, баннер показывает «Ходов в
  очереди: N»;
* даже **перезагрузка вкладки без интернета** показывает поле и очередь из сохранённой копии.

### 5.4. Синхронизация после переподключения

Клиент отправляет `hello { token, roundId, lastSeq }`. Сервер выбирает, что прислать:

| Ситуация | Ответ |
|---|---|
| тот же раунд, `lastSeq` = текущий | дельта из 0 изменений |
| тот же раунд, отстал на ≤ 2000 изменений | **дельта**: `SELECT … FROM moves WHERE seq > lastSeq AND status = 'ok'` |
| отстал сильнее, другой раунд, первый вход | **снимок** всего поля |

Это и есть **дельта-синхронизация по журналу событий**. Тот же принцип у репликации
БД по WAL и в Event Sourcing.

Расчёт синхронизации и отправка `welcome` выполняются **внутри очереди ходов**, а рассылки
клиенту начинаются только после `welcome` (флаг `ready`). Поэтому между снимком и первым
`pixel` не может «проскочить» ни одно изменение.

Клиент применяет изменения по правилу **«побеждает бо́льшая версия клетки»**. Так порядок
прихода сообщений (`paintResult`, `pixel`, дельта) не важен, а повторно пришедшее изменение ничего
не портит.

### 5.5. Повторная отправка без дублей (идемпотентность)

После `welcome` клиент досылает очередь. Проблема: связь могла оборваться **после** того, как
сервер применил ход, но **до** того, как ответ дошёл до клиента. Тогда клиент отправит этот ход
ещё раз.

Решение — **`actionId`** (UUID, генерирует клиент) и `UNIQUE (player_id, action_id)` в `moves`.
Перед обработкой сервер ищет ход с таким `actionId`; если он уже есть, сервер возвращает прежний
результат с `duplicate: true` и **ничего не меняет**. Это стандартный приём для надёжной доставки:
доставка «как минимум один раз» плюс идемпотентный обработчик дают эффективно «ровно один раз».
Так же устроены `Idempotency-Key` в платёжных API.

Ходы из очереди проверяются по **тем версиям клеток, которые игрок видел офлайн**. Если клетку
за это время кто-то перекрасил, ход получает `conflict`. В конце игрок видит итог:
«Офлайн-ходы отправлены: применено 3, отклонено из-за конфликтов 1». Если пока игрок был офлайн
сменился раунд, его очередь отменяется с предупреждением, потому что старые ходы к новому полю
не относятся.

Если сервер не смог обработать ход (например, недоступна БД), ответ `status: 'error'`: ход
остаётся в очереди и отправляется повторно через 2 с.

## 7. Надёжность и безопасность (о чём могут спросить)

* **Никакого доверия клиенту.** Каждое сообщение проверяется в `protocol.js`: тип, набор полей,
  целые координаты в пределах поля, UUID, длина имени и отсутствие управляющих символов. Ошибка
  приходит в ответ как `error`, а соединение не рвётся.
* **Команду игрока берёт сервер** из БД, а не из сообщения: покрасить «за чужую команду» нельзя.
* **Ограничение частоты** (token bucket: 25 сообщений в секунду, всплеск до 50) на каждое
  соединение. При злостном флуде соединение закрывается с кодом `1008`. Размер сообщения
  ограничен 16 КБ (`maxPayload`).
* **Медленные клиенты** (накопилось больше 1 МБ неотправленного) перестают получать курсоры,
  чтобы не раздувать память сервера (backpressure).
* **XSS невозможен через имена**: на клиенте данные игроков выводятся только через
  `textContent` и Canvas, `innerHTML` не используется. Плюс строгая **Content-Security-Policy**:
  скрипты, стили и соединения только со своего origin.
* **Path traversal**: `static.js` нормализует путь и проверяет, что файл лежит внутри `public/`.
* **Корректная остановка**: на `SIGTERM` клиенты получают код `1001` и переподключаются сами,
  а ходы, уже стоящие в очереди, успевают записаться в БД.
* **Журнал** — JSON-строки в stdout (`event`: `game.loaded`, `player.joined`, `paint.conflict`,
  `round.finished`, `ws.timeout`, `ws.flood`, `http.request`…).

## 9. Сценарий демонстрации

1. `cd Lab4 && docker compose up --build`, открыть <http://localhost:8092> в **двух окнах**
   (обычном и приватном), войти разными игроками в разные команды.
2. **Синхронизация**: клик в одном окне — клетка мгновенно появляется во втором; видно курсор
   соседа, счёт и список онлайн меняются.
3. **Конфликт**: в DevTools одного окна → Network → Offline; закрасить клетку X; во втором окне
   закрасить ту же клетку X; вернуть сеть → в первом окне красный крестик и «отклонено из-за
   конфликтов 1».
4. **Офлайн**: DevTools → Offline, нарисовать несколько клеток (пунктир, баннер «Ходов в
   очереди: N»), **перезагрузить вкладку** (поле и очередь на месте), вернуть сеть → ходы
   отправились.
5. **Перезапуск сервера**: `docker compose restart app` → в окнах «Нет связи · повтор через…»,
   через пару секунд снова «В сети», поле на месте.
6. **Сохранение**: `docker compose down && docker compose up -d` → игра продолжается с того же места.
7. **Журнал**: `docker compose logs app | grep paint.conflict`.

## 10. Вопросы на защите

**Почему WebSocket, а не HTTP-запросы раз в секунду?** Двусторонний канал без задержки и без
лишних запросов; сервер сам сообщает о событии в момент, когда оно произошло.

**Что такое «авторитетный сервер»?** Клиент лишь присылает намерение («хочу закрасить»), а
сервер решает, применить ли его, и рассылает результат. Клиент не может обмануть игру, подменив
состояние у себя.

**Зачем очередь, если Node.js однопоточный?** Однопоточность защищает только синхронный код.
Обработка хода содержит `await`, и во время ожидания БД начал бы обрабатываться другой ход.

**Почему версия, а не время изменения?** Часы клиентов и даже серверов расходятся, а версия —
точный счётчик: «ты видел изменение №5, а сейчас уже №6».

**Что увидит игрок при конфликте?** Свой ход откатится, на клетке мигнёт красный крестик,
появится сообщение, кто её перекрасил, и заряд вернётся.

**Как гарантируется, что ход не применится дважды?** `actionId` + `UNIQUE (player_id, action_id)`:
повтор возвращает прежний результат.

**Как клиент узнаёт, что пропустил?** По `lastSeq` — порядковому номеру последнего известного
изменения. Сервер присылает из журнала `moves` всё, что новее.

**Почему иногда приходит снимок, а не дельта?** Если клиент отстал сильно (больше 2000 изменений)
или раунд сменился, всё поле целиком отправить дешевле.

**Что будет при перезапуске сервера во время игры?** Клиенты получат код 1001 или заметят обрыв,
переподключатся с нарастающей задержкой и получат дельту. Состояние в БД, поэтому ничего не
теряется.

**Где здесь «без фреймворков», если есть npm-пакеты?** `ws` и `pg` — библиотеки: протокол
WebSocket и драйвер БД. Архитектура, маршрутизация, синхронизация и интерфейс написаны на чистом
JavaScript.

**Как масштабировать на несколько серверов?** Рассылку — через общий канал (Redis Pub/Sub или
PostgreSQL `LISTEN/NOTIFY`), очередь — заменить блокировкой в БД (условная запись уже есть).
Сейчас один процесс, что для лабораторной достаточно и проще объяснить.
