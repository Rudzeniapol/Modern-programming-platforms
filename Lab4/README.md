# Лабораторная работа №4 — «Пиксельная битва»

Многопользовательская веб-игра в реальном времени. Четыре команды делят одно поле
64×40 клеток и закрашивают клетки цветом своей команды. У кого к концу раунда (10 минут)
больше территории, тот победил; затем поле очищается и начинается новый раунд.

Теория к защите — что где лежит, как устроено и почему — в [THEORY.md](THEORY.md).

| Требование | Как выполнено |
|---|---|
| Мгновенная синхронизация через WebSockets | каждый ход сразу рассылается всем подключённым; видны курсоры других игроков, счёт и список онлайн |
| Только JavaScript, без фреймворков | клиент — ES-модули и Canvas без React и без сборщика; сервер — встроенный модуль `http` без Express. Из зависимостей только `ws` (реализация протокола WebSocket) и `pg` (драйвер PostgreSQL) |
| Сохранение данных между запусками | поле, игроки, заряды, журнал ходов и история раундов с итоговыми картами — в PostgreSQL; после перезапуска игра продолжается с того же места |
| *Доп. 1.* Конкурентный доступ, разрешение конфликтов | у каждой клетки есть версия; ход проходит, только если клетка не изменилась с тех пор, как игрок её увидел (оптимистическая блокировка). При конфликте выигрывает тот, чей ход сервер обработал первым; второй игрок видит, кто его опередил, и заряд ему возвращается |
| *Доп. 2.* Потеря соединения | состояние сохраняется в `localStorage`; ходы без связи копятся в очереди; переподключение автоматическое; после него клиент получает только пропущенные изменения и досылает очередь (без дублей благодаря `actionId`) |
| *Доп. 3.* Хостинг | готовы `Dockerfile` и Blueprint для Render (`render.yaml` в корне репозитория) |

## Запуск

```bash
cd Lab4
docker compose up --build
```

Откройте <http://localhost:8092> в нескольких окнах (или в обычном и приватном), войдите
под разными именами в разные команды и рисуйте.

```bash
docker compose logs -f app   # журнал (JSON)
docker compose down          # остановить; данные остаются в томе pgdata
docker compose down -v       # остановить и удалить все данные
```

Параметры (порт, длительность раунда, заряды) задаются в `.env` (шаблон — `.env.example`).

## Правила

* Кликните по клетке, и она станет цвета вашей команды. Чужую клетку можно перекрасить.
* **Заряды**: не больше 10 клеток подряд, потом по одной каждые 3 секунды.
* **Раунд** длится 10 минут. Побеждает команда с наибольшей территорией; при равенстве — ничья.
* **История** под полем — последние сыгранные раунды: итоговая карта, победитель и команды,
  которые играли (сколько клеток было у каждой к концу и сколько игроков участвовало). Раунды,
  в которых никто не играл, в историю не попадают.
* Без входа можно смотреть игру как зритель.

## Как это устроено

```
браузер (чистый JS)                               Node.js (один процесс, один порт)
┌──────────────────────────┐   WebSocket /ws   ┌────────────────────────────────────┐
│ Connection — переподкл., │◄─────────────────►│ Hub — соединения, рассылка,        │
│   ping, online/offline   │   JSON-сообщения  │   heartbeat, лимит частоты         │
│ GameState — поле, очередь│                   │ Game — авторитетное состояние,     │
│   ходов, localStorage    │   HTTP GET        │   очередь ходов, раунды, заряды    │
│ BoardRenderer — Canvas   │◄─────────────────►│ http — статика + /api/health       │
│ UI — DOM, уведомления    │                   └───────────────┬────────────────────┘
└──────────────────────────┘                                   │ pg
                                                     PostgreSQL: players, rounds,
                                                     cells, moves
```

**Сервер авторитетен**: клиент только *просит* закрасить клетку, а решение принимает
сервер. Все ходы обрабатываются строго по одному (`SerialQueue`) и сначала фиксируются в
БД транзакцией, и только потом применяются к полю в памяти и рассылаются.

### Протокол (JSON поверх WebSocket)

| Направление | Сообщение | Назначение |
|---|---|---|
| → | `hello { token, roundId, lastSeq }` | представиться после (пере)подключения; сообщить, до какого изменения клиент знает поле |
| ← | `welcome { config, round, player, sync, scores, online, history, serverTime }` | синхронизация: `sync` — снимок поля или только пропущенные изменения |
| → | `join { name, team }` / ← `joined { token, player }` | первый вход: сервер выдаёт токен игрока |
| → | `paint { actionId, x, y, baseVersion, roundId }` | ход: `baseVersion` — версия клетки, которую видел игрок |
| ← | `paintResult { actionId, status, cell, player }` | `ok` / `conflict` / `no_charges` / `rejected` / `error` |
| ← | `pixel { seq, x, y, team, version, playerName }` | всем: клетка перекрашена |
| ↔ | `cursor { x, y }` / ← `cursorGone` | курсоры других игроков (не сохраняются) |
| ← | `presence`, `scores` | кто онлайн, текущий счёт |
| ← | `roundEnd { roundId, winnerTeam, scores, board }` / `roundStart` | конец раунда с итоговым счётом и итоговой картой; начало нового |
| ↔ | `ping { t }` / `pong` | задержка и проверка, что соединение живо |
| ← | `error { code, message }` | ошибка протокола: соединение при этом не рвётся |

### Конфликты одновременного изменения

```
Алиса и Боб видят клетку (7,7) пустой, версия 0
Алиса: paint (7,7) baseVersion=0  ─┐
Боб:   paint (7,7) baseVersion=0  ─┤ сервер обрабатывает по одному
                                   ├─► Алиса: версия 0 = 0 → ok, клетка версии 1, всем pixel
                                   └─► Боб:   версия 1 ≠ 0 → conflict, получает актуальную клетку,
                                              заряд не списан, на поле — красный крестик и подсказка
```

В БД запись клетки тоже условная (`UPDATE … WHERE version = $base`), то есть защита
двойная. Политика разрешения — **first-write-wins**: первым применяется тот ход, который
сервер обработал первым, а ход по устаревшей версии отклоняется.

### Обрыв связи

1. Клиент замечает потерю связи сразу: по событиям `offline`/`close` или по таймауту ping
   (12 с без сообщений от сервера).
2. Наверху появляется баннер. Рисовать можно и дальше: ходы показываются пунктиром и копятся в
   очереди, а очередь и поле сохраняются в `localStorage` (переживают перезагрузку вкладки).
3. Переподключение идёт автоматически с экспоненциальной задержкой со случайным разбросом:
   0,5 → 1 → 2 → … → 10 с.
4. В `hello` клиент передаёт `roundId` и `lastSeq`, и сервер присылает только изменения
   после `lastSeq` из журнала `moves`. Если клиент отстал больше чем на 2000 изменений или
   раунд сменился, приходит снимок всего поля.
5. Клиент досылает очередь. У каждого хода есть `actionId`, а `UNIQUE (player_id, action_id)` в
   БД гарантирует, что ход, уже применённый до обрыва, не применится второй раз. Клетки,
   изменённые за время офлайна, получают `conflict`, и игрок видит итог:
   «применено N, отклонено M».

## Развёртывание на Render

1. Выложить репозиторий на GitHub.
2. <https://dashboard.render.com> → **New → Blueprint** → выбрать репозиторий: Render прочитает
   `render.yaml` из корня и создаст веб-сервис (Docker, `Lab4/Dockerfile`) и PostgreSQL.
3. Через несколько минут приложение доступно по адресу `https://spp-pixel-battle.onrender.com`
   (или похожему). WebSocket работает по `wss://` на том же адресе.

Ограничения бесплатного тарифа Render: сервис засыпает после 15 минут без запросов (первое
открытие после этого занимает ~1 минуту), бесплатная база живёт 30 дней. Вместо неё можно
взять бесплатный PostgreSQL на [Neon](https://neon.tech): указать его строку подключения в
`DATABASE_URL` и `DATABASE_SSL=true`.
